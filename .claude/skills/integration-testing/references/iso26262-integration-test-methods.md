# ISO 26262-6 기반 소프트웨어 통합시험 기법

이 참조는 A-SPICE 4.1 SWE.5(소프트웨어 통합 및 통합시험) BP와 ISO 26262-6(소프트웨어 개발) Part 6에서 공개적으로 알려진 "소프트웨어 통합시험 방법"과 "통합시험 케이스 도출 기법"을 재구성한 것입니다.

**중요**: 아래 내용은 원문 표준의 축약이 아니라 공개적으로 알려진 원칙을 재구성한 실무 참조 자료이며, ASIL별 정확한 권고 강도(+/++)는 표기하지 않습니다. 계약/인증 목적의 공식 판정에는 원본 ISO 26262-6 표(소프트웨어 통합시험 방법/기법 표)를 대조해야 함을 사용자에게 필요 시 안내하세요.

## A-SPICE SWE.5 Base Practice — 산출물에 반드시 반영

| BP | 반드시 반영할 산출물 |
|---|---|
| 통합 전략 수립 | 통합 원칙, 통합 항목·순서 (아키텍처 설계서 11장 "통합 전략"과 일치) |
| 통합 검증 기준 정의 | 진입/종료 기준 |
| 통합 테스트 케이스 설계 (아키텍처 기반) | 인터페이스별 테스트 케이스, 사용 기법 |
| 통합 수행 및 결과 기록 | 실행 결과, 증거 위치 |
| 회귀 전략 | 변경 영향 기반 회귀 범위 |
| 양방향 추적성 (아키텍처↔통합테스트) | 인터페이스 ↔ 테스트 케이스 ↔ 실행 결과 추적 |

## 소프트웨어 통합시험 방법 (무엇을 검증하는가)

| 방법 | 설명 | 이 프로젝트 적용 |
|---|---|---|
| 요구사항 기반 시험 (Requirements-based test) | 아키텍처/SW 요구사항에 명시된 동작을 통합된 컴포넌트 집합에 대해 검증 | 모든 통합 단계에서 항상 적용 |
| 인터페이스 시험 (Interface test) | 아키텍처 설계서의 인터페이스 명세(제공자/사용자/데이터계약/사전·사후조건/오류계약)를 그대로 시험 케이스로 변환 | 모든 통합 단계에서 항상 적용 — 이 스킬의 핵심 |
| 결함 주입 시험 (Fault injection test) | 인터페이스 오류 계약(잘못된 입력, 통신 실패 등)이 정의대로 처리되는지 의도적으로 결함을 주입해 검증 | 오류 계약이 정의된 인터페이스, 안전 관련(ASIL) 인터페이스에 우선 적용 |
| 자원 사용 시험 (Resource usage test) | 통합 후 실제 자원 사용(메모리/CPU/타이밍)이 아키텍처의 자원 분석과 일치하는지 검증 | 아키텍처 13장 "자원 및 배포 경계"에 자원 제약이 명시된 경우 적용 |
| 모델-코드 백투백 비교 시험 (Back-to-back comparison) | 모델 기반 개발을 사용하는 경우 모델과 코드의 동작을 비교 | 모델 기반 개발을 사용하지 않으면 해당 없음으로 표시 |

## 통합시험 케이스 도출 기법 (어떻게 케이스를 만드는가)

기법의 정의와 전체 목록은 **`sw-quality-standards` 스킬의 `references/iso29119.md`(ISO/IEC/IEEE 29119 Part 4)를 단일 출처**로 사용합니다 — `tdd`, `sw-system-test` 스킬과 동일한 명칭·정의를 그대로 씁니다. 이 문서에서 기법을 다시 정의하지 않고, 통합시험에서 각 기법을 어떤 대상에 적용하는지만 정리합니다.

| 기법 | 통합시험에서의 적용 |
|---|---|
| 요구사항 분석 (Analysis of requirements) | 아키텍처 요구사항 할당표(12장)에서 통합 단위가 만족해야 할 요구사항을 도출 |
| 동등분할 | 인터페이스 데이터 계약의 유효/무효 입력 클래스별 대표 케이스 |
| 경계값 분석 | 인터페이스 데이터 계약의 유효 범위 경계값 |
| 결정 테이블 테스팅 | 여러 인터페이스 입력 조합에 따라 동작이 달라지는 통합 시나리오 |
| 상태 전이 테스팅 | 아키텍처 8장 상태전이가 통합된 컴포넌트 간 이벤트로 실제 발생하는지 검증 |
| 오류 추정 | 인터페이스 오류 계약 외에 통합 경계에서 발생하기 쉬운 결함(순서 오류, 타이밍 위반 등) 추정 |

인터페이스 입력 파라미터가 많아 조합 폭발이 우려되는 경우 `iso29119.md`의 조합 테스트/페어와이즈 테스팅을 사용할 수 있으나, 이는 예외적인 경우이며 SW 요구사항 전반의 조합을 체계적으로 다루는 것은 `sw-system-test` 스킬의 몫입니다.

## 케이스 설계 절차

1. 대상 통합 단계(아키텍처 11장/`TPL-SWE5-001` 3장 "통합 항목과 순서"의 한 단계)에서 새로 연결되는 인터페이스 목록을 확인합니다.
2. 각 인터페이스에 대해 위 "통합시험 방법" 중 최소 요구사항 기반 시험 + 인터페이스 시험을 기본 적용하고, 오류 계약이 있으면 결함 주입 시험을 추가합니다.
3. 각 시험에 대해 위 "케이스 도출 기법" 표에서 근거 기법을 선택해 케이스를 만듭니다 — 근거 기법 없이 임의로 값을 고르지 않습니다.
4. 케이스마다 대응 인터페이스 ID, 사용 기법, 긍정/부정 케이스 여부를 명시합니다 (부정 케이스는 `tdd` 스킬의 `test-documentation-style.md`와 동일한 원칙).
