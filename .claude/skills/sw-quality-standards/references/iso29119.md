# ISO/IEC/IEEE 29119 — SW 동적 테스팅 표준

ISO/IEC/IEEE 29119는 소프트웨어 테스팅에 대한 국제 표준 시리즈로, 조직 차원의 테스트 정책부터 테스트 설계 기법까지 다룹니다. "동적 테스팅"이란 소프트웨어를 실제로 실행하여 검증하는 것을 말하며(정적 리뷰/분석과 대비), 이 참조 파일은 실무에서 가장 많이 쓰이는 Part 2(테스트 프로세스), Part 3(테스트 문서), Part 4(테스트 설계 기법)를 중심으로 정리합니다.

## 구성 (Part 개요)

| Part | 내용 |
|---|---|
| Part 1 | 개념과 용어 정의 |
| Part 2 | 테스트 프로세스 (조직 테스트 프로세스, 테스트 관리 프로세스, 동적 테스트 프로세스) |
| Part 3 | 테스트 문서 및 템플릿 |
| Part 4 | 테스트 설계 기법 (블랙박스/화이트박스/경험 기반) |
| Part 5 | 키워드 기반 테스팅 |

## 동적 테스트 프로세스 (Part 2)

동적 테스트 프로세스는 아래 활동으로 구성됩니다. CL2(A-SPICE) 감사와 달리, 이 표준은 "각 활동이 실제로 수행되고 문서화되었는가"에 초점을 둡니다.

| 단계 | 활동 | 대표 산출물 |
|---|---|---|
| 테스트 계획 (Test Planning) | 테스트 범위, 목표, 전략, 자원, 일정 수립 | 테스트 계획서 (Test Plan) |
| 테스트 모니터링 및 통제 | 계획 대비 진척 추적, 이탈 시 조정 | 테스트 진척 보고서 |
| 테스트 분석 (Test Analysis) | 테스트 대상(요구사항/설계 등)으로부터 테스트 조건 도출 | 테스트 분석 결과, 테스트 조건 목록 |
| 테스트 설계 (Test Design) | 테스트 조건으로부터 테스트 케이스/절차 설계 | 테스트 설계 명세서, 테스트 케이스 명세서 |
| 테스트 구현 (Test Implementation) | 테스트 절차, 테스트 데이터, 테스트 환경 준비 | 테스트 절차 명세서, 테스트 데이터, 테스트 환경 |
| 테스트 실행 (Test Execution) | 테스트 케이스 실행, 실제 결과와 기대 결과 비교 | 테스트 실행 로그, 테스트 결과(Pass/Fail) |
| 테스트 완료 (Test Completion) | 결과 정리, 재사용 자산 보존, 완료 보고 | 테스트 완료 보고서 (Test Completion Report) |

**점검 포인트**: 프로젝트에 "테스트 결과"만 있고 "테스트 분석/설계" 산출물이 없는 경우가 흔합니다 — 이는 테스트 케이스가 요구사항으로부터 체계적으로 도출된 것이 아니라 임기응변으로 작성되었을 가능성을 시사하므로 갭으로 지적하세요.

## 테스트 문서 (Part 3) — 대표 템플릿과 필수 내용

| 문서 | 필수 내용 |
|---|---|
| 테스트 계획서 (Test Plan) | 테스트 범위, 목표, 접근법(전략), 진입/종료 기준, 일정, 자원, 리스크 |
| 테스트 설계 명세서 | 테스트 대상, 테스트 조건, 적용된 설계 기법 |
| 테스트 케이스 명세서 | 케이스 ID, 사전조건, 입력값, 기대결과, 요구사항 추적 링크 |
| 테스트 절차 명세서 | 실행 순서, 필요한 테스트 데이터/환경 |
| 테스트 상태 보고서 | 진행률, 발견된 결함, 리스크 |
| 테스트 완료 보고서 | 요약 결과, 커버리지, 잔존 리스크, 교훈(lessons learned) |

**점검 포인트**: 각 문서가 요구사항/설계와의 추적성(traceability)을 갖고 있는지 확인하세요. 추적성이 없으면 "이 테스트가 무엇을 검증하는지"를 재구성할 수 없어 유지보수 시 테스트 커버리지가 빠르게 붕괴됩니다.

## 테스트 설계 기법 (Part 4)

### 블랙박스 기법 (명세 기반)
- **동등분할 (Equivalence Partitioning)**: 입력값을 동등한 그룹으로 나누고 그룹별 대표값으로 테스트
- **경계값 분석 (Boundary Value Analysis)**: 입력 범위의 경계 및 경계 근처 값 테스트
- **결정 테이블 테스팅 (Decision Table Testing)**: 여러 조건의 조합에 따른 결과를 표로 정리해 테스트
- **상태 전이 테스팅 (State Transition Testing)**: 시스템의 상태와 상태 전이를 기반으로 테스트
- **분류 트리법 (Classification Tree Method)**: 입력을 분류 기준별로 트리 형태로 조합해 테스트

### 화이트박스 기법 (구조 기반)
- **구문 커버리지 (Statement Coverage)**: 모든 코드 라인이 최소 1회 실행되는지
- **분기 커버리지 (Branch/Decision Coverage)**: 모든 분기(if/else 등)가 참/거짓 모두 실행되는지
- **조건 커버리지 (Condition Coverage)**: 복합 조건의 각 하위 조건이 모두 평가되는지
- **MC/DC (Modified Condition/Decision Coverage)**: 안전 필수 시스템(항공, 자동차)에서 요구되는 고강도 커버리지 기준 — 각 조건이 독립적으로 전체 결과에 영향을 미치는 경우를 모두 테스트

### 경험 기반 기법
- **탐색적 테스팅 (Exploratory Testing)**: 사전 설계된 케이스 없이 탐색하며 테스트 설계/실행을 동시에 수행
- **오류 추정 (Error Guessing)**: 경험을 바탕으로 결함이 있을 법한 영역을 추정해 테스트

**점검 포인트**: 안전 필수(safety-critical) 소프트웨어(자동차 SW 등)의 유닛/통합 테스트에서 MC/DC 등 고강도 커버리지 기준이 요구됨에도 단순 구문/분기 커버리지만 측정하고 있다면 Major 갭으로 지적하세요.

## 점검 시 활용 방법

1. 대상 프로젝트의 테스트 산출물을 위 "동적 테스트 프로세스" 표의 7단계에 매핑합니다. 어느 단계의 산출물이 비어 있는지 먼저 식별하세요.
2. 테스트 케이스가 어떤 설계 기법을 사용했는지(명시적으로 기술되어 있지 않더라도 케이스 패턴에서 추정 가능) 확인하고, 요구사항의 특성에 적합한 기법이 사용되었는지 평가합니다 (예: 상태 기반 기능인데 상태 전이 테스팅이 전혀 없는 경우).
3. 커버리지 목표가 프로젝트/도메인 요구 수준(예: 안전 필수 코드의 MC/DC)에 맞게 설정되어 있는지 확인합니다.
4. A-SPICE 감사와 함께 수행할 경우, 이 표준의 테스트 설계/문서 점검 결과를 `aspice-auditor` 스킬의 SWE.4/SWE.5/SWE.6, SYS.4/SYS.5 산출물 점검과 연계하세요.
