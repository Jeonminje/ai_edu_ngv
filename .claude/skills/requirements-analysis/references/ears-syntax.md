# EARS (Easy Approach to Requirements Syntax)

EARS는 요구사항을 정해진 5가지 문장 패턴 중 하나로 작성하도록 강제해, 모호성·복합성·미검증가능성 문제를 구조적으로 줄이는 업계에서 널리 쓰이는 요구사항 작성 방식입니다. 모든 패턴은 기본적으로 "<트리거/조건> 시스템은 <동작>해야 한다" 형태를 따릅니다.

## 5가지 패턴

### 1. 유비쿼터스 (Ubiquitous) — 항상 참인 요구사항
조건 없이 항상 적용되는 요구사항.

**템플릿**: `<시스템명>은 <동작>해야 한다.`

**예시**: "시스템은 모든 사용자 입력을 UTF-8로 인코딩해야 한다."

### 2. 이벤트 기반 (Event-Driven) — 특정 이벤트 발생 시
트리거 이벤트가 발생했을 때만 적용.

**템플릿**: `WHEN <트리거 이벤트>, <시스템명>은 <동작>해야 한다.`

**예시**: "WHEN 사용자가 '저장' 버튼을 클릭하면, 시스템은 현재 문서를 저장소에 기록해야 한다."

### 3. 상태 기반 (State-Driven) — 특정 상태 동안
특정 상태가 지속되는 동안 적용.

**템플릿**: `WHILE <상태>, <시스템명>은 <동작>해야 한다.`

**예시**: "WHILE 차량이 시속 30km 이상으로 주행 중일 때, 시스템은 도어 잠금을 해제하는 명령을 거부해야 한다."

### 4. 원치 않는 동작 (Unwanted Behaviour) — 예외/오류 처리
바람직하지 않은 조건이 발생했을 때의 처리.

**템플릿**: `IF <원치 않는 조건>, THEN <시스템명>은 <동작>해야 한다.`

**예시**: "IF 센서로부터 3초 이상 데이터를 수신하지 못하면, THEN 시스템은 안전 모드로 전환하고 경고를 표시해야 한다."

### 5. 옵션 기능 (Optional Feature) — 특정 기능 구성 시에만
제품 변형(variant)에 따라 존재하는 기능에 대한 요구.

**템플릿**: `WHERE <기능/옵션이 포함된 경우>, <시스템명>은 <동작>해야 한다.`

**예시**: "WHERE 차량에 어댑티브 크루즈 컨트롤 옵션이 장착된 경우, 시스템은 선행 차량과의 거리를 유지해야 한다."

### 6. 복합 패턴 (Complex) — 위 패턴의 조합
여러 조건이 동시에 필요할 때 위 패턴을 조합.

**템플릿**: `WHILE <상태>, WHEN <트리거>, <시스템명>은 <동작>해야 한다.`

**예시**: "WHILE 시스템이 자율주행 모드일 때, WHEN 운전자가 스티어링 휠을 잡으면, 시스템은 수동 모드로 전환해야 한다."

## 재작성 워크플로우

모호하거나 복합적인 요구사항을 발견하면 다음 순서로 재작성을 제안하세요:

1. **트리거/조건 분리**: 문장에서 "~일 때", "~하면", "~하는 동안" 같은 조건절을 찾아 어떤 패턴(이벤트/상태)에 해당하는지 식별합니다.
2. **동작 단일화**: "그리고"로 연결된 여러 동작이 있으면 요구사항을 분리합니다. 하나의 EARS 문장에는 하나의 결과 동작만 남깁니다.
3. **정량 기준 삽입**: "빠르게", "충분히" 등 모호한 부사를 구체적 수치/조건으로 치환합니다. 수치를 사용자가 모르면 TBD로 표시하고 별도로 확정이 필요함을 알립니다.
4. **주어를 명확히**: "<시스템명>"에 실제 대상 구성요소명을 넣어 어떤 구성요소의 책임인지 명확히 합니다 (아키텍처 배분·추적성에 필요).

## 주의사항

- EARS는 형식을 강제할 뿐 요구사항의 정확성(실제 이해관계자 니즈 반영)을 보장하지 않습니다. 형식이 맞아도 내용이 틀린 요구사항일 수 있으니 `requirement-quality.md`의 "일치함(Correct)"과 "필요함(Necessary)" 기준도 함께 점검하세요.
- 모든 요구사항을 무리하게 EARS 패턴에 끼워 맞추지 마세요. 배경 설명, 용어 정의, 가정사항 같은 비-요구사항 텍스트는 별도 섹션으로 분리하는 것이 낫습니다.
