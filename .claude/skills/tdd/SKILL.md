# TDD 구현 스킬

이 스킬은 [obra/superpowers](https://github.com/obra/superpowers)의 `test-driven-development` 스킬을 기반으로, 이 프로젝트(CLAUDE.md 구현 지침)에 맞게 Python 3.14 + `unittest`로 재구성한 것입니다. superpowers 원본의 "철칙(Iron Law)"과 Red-Green-Refactor 규율은 그대로 유지하고, 이 프로젝트 고유의 품질 지표·네이밍·주석·상세설계 연계 요구사항을 결합했습니다.

**중요**: CLAUDE.md의 지침이 이 스킬의 내용과 상충하면 항상 CLAUDE.md가 우선합니다.

## 철칙 (Iron Law)

```
실패하는 테스트 없이 프로덕션 코드를 작성하지 않는다.
```

테스트보다 먼저 구현 코드를 작성했다면 — **삭제하고 다시 시작합니다.**
- "참고용으로만 남겨두기" 금지
- 테스트를 작성하면서 그 코드를 "적당히 손봐서" 재사용하기 금지
- 쳐다보지도 말고, 처음부터 테스트에서 새로 구현합니다

"이번만 TDD 건너뛰자"는 생각이 든다면 — 그것이 바로 합리화 신호입니다.

## 언제 적용하는가

**항상 적용**: 신규 기능, 버그 수정, 리팩터링, 동작 변경 — CLAUDE.md에 따라 이 프로젝트는 예외를 허용하지 않습니다.

**예외가 필요하다고 판단되면** (일회성 프로토타입, 자동 생성 코드, 설정 파일 등) 임의로 건너뛰지 말고 반드시 사용자에게 확인을 받습니다.

## 입력: 상세설계서 확인

구현은 승인된 상세설계서(`detailed-design` 스킬 산출물, `TPL-SWE3-001`)의 함수 계약(입력/출력/사전조건/사후조건/부작용/예외/경계값), 결정 테이블, 오류 처리 정의를 근거로 시작합니다. 상세설계서가 없거나 대상 범위가 확인되지 않으면 구현을 시작하지 말고 사용자에게 확인을 요청합니다 → `references/design-to-code-traceability.md`

## Red-Green-Refactor 사이클

```
RED (실패하는 테스트 작성) → Verify RED (반드시 실패 확인)
   → GREEN (최소 구현) → Verify GREEN (반드시 통과 확인)
   → REFACTOR (정리, 초록 유지) → 다음 테스트로 반복
```

### RED — 실패하는 테스트 작성

상세설계서의 함수 계약 1개, 경계값 1개, 또는 결정 테이블의 조건 조합 1개에 대응하는 `unittest.TestCase` 테스트를 작성합니다. 한 번에 하나의 동작만 검증합니다.

각 테스트 함수에는 **반드시** `references/test-documentation-style.md`에 따라 Doxygen 형식의 목적 설명, 사용한 테스트 기법, 긍정/부정 케이스 여부를 함께 작성합니다.

<Good>
```python
class TestRetryOperation(unittest.TestCase):
    ## @brief 3회 실패 후 성공하면 재시도 로직이 성공 결과를 반환하는지 검증한다.
    #  @technique 동등분할 (성공 전환 흐름 클래스)
    #  @case 긍정 (Positive)
    def testRetriesFailedOperationThreeTimes(self):
        attempts = {"count": 0}

        def operation():
            attempts["count"] += 1
            if attempts["count"] < 3:
                raise RuntimeError("fail")
            return "success"

        result = retryOperation(operation)

        self.assertEqual(result, "success")
        self.assertEqual(attempts["count"], 3)
```
이름이 명확하고, 실제 동작을 검증하며, 한 가지만 확인합니다.
</Good>

<Bad>
```python
class TestRetry(unittest.TestCase):
    def testRetryWorks(self):
        mockOp = Mock(side_effect=[RuntimeError(), RuntimeError(), "success"])
        retryOperation(mockOp)
        self.assertEqual(mockOp.call_count, 3)
```
이름이 모호하고, 실제 코드가 아니라 Mock의 호출 횟수만 검증합니다. 사용 기법/케이스 구분 주석도 없습니다.
</Bad>

**요구사항**: 하나의 동작, 명확한 이름, 실제 코드 검증(불가피한 경우만 Mock), Doxygen 목적 주석 + 기법 + 긍정/부정 표기.

### Verify RED — 실패를 눈으로 확인 (필수, 절대 생략 금지)

```bash
python -m unittest path.to.test_module -v
```

다음을 확인합니다:
- 테스트가 (에러가 아니라) **실패**하는가
- 실패 메시지가 예상한 이유(기능 미구현)로 발생했는가 — 오타 등 엉뚱한 이유로 실패한 것이 아닌가

**테스트가 바로 통과한다면** 이미 존재하는 동작을 테스트한 것입니다 — 테스트를 다시 검토합니다.
**테스트가 에러(오타 등)로 실패한다면** 에러를 고치고 "기능 미구현으로 인한 실패"가 나올 때까지 재실행합니다.

### GREEN — 테스트를 통과시키는 최소 구현

테스트를 통과시키는 데 필요한 최소한의 코드만 작성합니다. 아직 요구되지 않은 기능을 미리 만들지 않습니다(YAGNI). 구현 시점부터 `references/quality-gates.md`의 함수 라인수/순환복잡도 상한을 넘지 않도록 작은 함수로 나눕니다.

### Verify GREEN — 통과를 눈으로 확인 (필수)

```bash
python -m unittest discover -v
```

다음을 확인합니다:
- 새 테스트가 통과하는가
- 기존 테스트가 전부 여전히 통과하는가 (회귀 없음)
- 출력이 깨끗한가(에러/경고 없음)

**실패하면** 테스트가 아니라 코드를 고칩니다. **다른 테스트가 깨지면** 즉시 고칩니다.

### REFACTOR — 구조 개선 (초록 유지)

테스트가 통과하는 상태를 유지하면서:
- 중복 제거 (`references/quality-gates.md`의 중복 7라인 기준)
- 네이밍 정리 (camelCase, `references/naming-and-comment-style.md`)
- Doxygen 주석 보강(구현 함수 + 테스트 함수 모두)
- 헬퍼 함수 추출

새로운 동작을 추가하지 않습니다. 리팩터링 후 반드시 전체 테스트를 재실행하고, `references/quality-gates.md`의 오픈소스 도구로 품질 지표를 실측합니다.

### 반복

상세설계서의 다음 함수 계약/경계값/조건 조합/오류 처리 경로에 대해 위 사이클을 반복합니다. 모든 항목이 최소 1개 이상의 테스트로 커버될 때까지 계속합니다.

## 좋은 테스트의 조건

| 기준 | 좋음 | 나쁨 |
|---|---|---|
| **최소성** | 한 가지만 검증. 이름에 "그리고(and)"가 들어가면 분리 | `testValidatesEmailAndDomainAndWhitespace` |
| **명확성** | 이름이 동작을 설명 | `test1`, `testCase1` |
| **의도 표현** | 원하는 API/동작을 보여줌 | 코드가 뭘 해야 하는지 가려버림 |

테스트를 작성/수정할 때는 항상 `references/writing-good-tests.md`를 함께 읽으세요 — 테스트가 정직한지 검증하는 규칙(진짜로 실패할 수 있는지, Mock이 아니라 실제 동작을 검증하는지)이 담겨 있습니다.

## 흔한 합리화와 반박

| 변명 | 실제로는 |
|---|---|
| "너무 단순해서 테스트할 필요 없다" | 단순한 코드도 깨집니다. 테스트는 30초면 됩니다. |
| "나중에 테스트 작성하겠다" | 나중에 쓴 테스트는 바로 통과합니다 — 아무것도 증명하지 못합니다. 실제 동작이 아니라 구현을 검증하게 되고, 잊어버린 경계값을 놓칩니다. 실패를 본 적이 없으므로 버그를 잡을 수 있다는 증거가 없습니다. |
| "이미 수동으로 테스트해봤다" | 수동 테스트는 무엇을 확인했는지 기록이 없고, 코드가 바뀔 때 재실행할 수 없습니다. "될 때 됐다"는 포괄적 검증이 아닙니다. |
| "지우기엔 이미 쓴 시간이 아깝다" | 매몰비용의 오류입니다. 선택지는 TDD로 다시 쓰기(신뢰 가능) vs 신뢰할 수 없는 코드에 테스트를 나중에 붙이기(버그 가능성 높음)입니다. |
| "참고용으로 남겨두고 테스트부터 쓰겠다" | 결국 그 코드에 맞춰 테스트를 쓰게 됩니다 — 그것도 사후 테스트입니다. 삭제는 삭제입니다. |
| "테스트하기 어려운 건 설계가 불명확해서다" | 테스트가 어렵다는 신호를 들으세요. 테스트하기 어려우면 사용하기도 어렵습니다. |
| "TDD는 느리다" | TDD가 실용적인 길입니다. 커밋 전에 버그를 잡고, 회귀 걱정 없이 리팩터링하게 해줍니다. "실용적" 지름길은 결국 프로덕션에서 디버깅하는 것 — 더 느립니다. |

## 위험 신호 — 발견 즉시 중단하고 다시 시작

- 테스트보다 코드가 먼저 작성됨
- 구현 후에 테스트를 작성함
- 테스트가 작성하자마자 바로 통과함
- 왜 실패했는지 설명할 수 없음
- 테스트를 "나중에" 추가함
- "이번만 예외"라는 합리화
- "이미 수동으로 확인했다"
- "형식이 아니라 정신이 중요하다"
- 사용 기법/긍정·부정 케이스/Doxygen 목적 주석 없이 작성된 테스트

**이 중 하나라도 해당하면 코드를 삭제하고 TDD로 다시 시작합니다.**

## 버그 수정 예시

**버그**: 빈 이메일이 통과됨

```python
## @brief 이메일이 빈 문자열이면 제출이 거부되는지 검증한다.
#  @technique 경계값분석 (빈 문자열 — 최소 길이 경계)
#  @case 부정 (Negative)
def testRejectsEmptyEmail(self):
    result = submitForm({"email": ""})
    self.assertEqual(result["error"], "Email required")
```

**Verify RED**: `AssertionError: 'Email required' != None` (기능 미구현으로 실패 확인)

```python
## @brief 제출된 폼 데이터의 필수 항목을 검증하고 접수 결과를 반환한다.
#  @param formData 제출된 폼 데이터
#  @return 오류가 있으면 error 필드를 포함한 dict, 없으면 접수 결과
def submitForm(formData):
    if not formData.get("email", "").strip():
        return {"error": "Email required"}
    # ...
```

**Verify GREEN**: 통과. 리팩터링에서 다른 필수 필드 검증도 필요하면 공통 헬퍼로 추출합니다.

버그를 테스트 없이 고치지 않습니다 — 재현하는 실패 테스트를 먼저 작성하고 TDD 사이클을 따릅니다.

## 이 프로젝트 고유의 필수 제약 (CLAUDE.md, 예외 없음)

1. **`unittest` 사용**: 다른 프레임워크(pytest 등)를 임의로 도입하지 않습니다.
2. **품질 지표 준수**: 함수 순수 코드 50라인 이하, 순환복잡도 10 이하, 중복 7라인까지만 허용, Doxygen 주석 20% 이상, **Branch 커버리지 100%**, **테스트 성공률 100%** — 오픈소스 도구(`radon`, `pylint`, `coverage.py` 등)로 실측 → `references/quality-gates.md`
3. **네이밍은 camelCase**: 함수명/변수명/테스트 메서드명(`testXxx`) 모두 camelCase → `references/naming-and-comment-style.md`
4. **테스트 문서화**: 모든 테스트 함수는 Doxygen 목적 설명 + 사용 기법 + 긍정/부정 케이스 표기를 포함 → `references/test-documentation-style.md`
5. **상세설계와의 일관성**: 구현/테스트는 승인된 상세설계서의 계약을 근거로 하며 임의로 벗어나지 않습니다 → `references/design-to-code-traceability.md`

## 막혔을 때

| 문제 | 해결 |
|---|---|
| 테스트를 어떻게 짤지 모르겠다 | 원하는 API를 먼저 상상해서 적어봅니다. Assertion부터 씁니다. 필요하면 사용자에게 확인합니다. |
| 테스트가 너무 복잡하다 | 설계가 복잡한 것입니다. 인터페이스를 단순화하세요. |
| 모든 걸 Mock해야 한다 | 코드가 과도하게 결합되어 있습니다. 의존성 주입을 사용하세요 (`architecture-design` 스킬의 결합도 원칙 참조). |
| 테스트 준비(setup)가 방대하다 | 헬퍼로 추출하세요. 그래도 복잡하면 설계를 단순화하세요. |

- [ ] 모든 신규 함수/메서드에 대응하는 테스트가 있는가?
- [ ] 각 테스트가 구현 전에 실패하는 것을 실제로 확인했는가(Verify RED)?
- [ ] 각 테스트가 예상한 이유(기능 미구현)로 실패했는가 (오타 등이 아님)?
- [ ] 각 테스트를 통과시키는 최소한의 코드만 작성했는가?
- [ ] 전체 테스트가 통과하는가(Verify GREEN, 회귀 없음)?
- [ ] 출력이 깨끗한가(에러/경고 없음)?
- [ ] 실제 코드를 검증하는가 (불가피한 경우만 Mock)?
- [ ] 경계값과 오류 케이스가 커버되는가?
- [ ] 모든 테스트 함수에 Doxygen 목적 주석 + 사용 기법 + 긍정/부정 케이스 표기가 있는가?
- [ ] 함수 순수 코드 50라인 이하 / 순환복잡도 10 이하 / 중복 7라인 이하 / 주석 20% 이상을 오픈소스 도구로 실측했는가?
- [ ] Branch 커버리지 100%를 오픈소스 도구(`coverage.py --branch`)로 실측했는가 (미달 시 갭을 해소하는 테스트를 추가했는가)?
- [ ] 전체 단위 테스트의 성공률이 100%인가 (실패한 테스트가 하나도 없는가)?
- [ ] 함수명/변수명/테스트 메서드명이 camelCase인가?
- [ ] 구현이 상세설계서의 계약과 일치하는가?

이 체크리스트를 모두 통과하지 못하면 TDD를 건너뛴 것입니다 — 처음부터 다시 시작합니다.

## 결과 보고 형식

```
### 구현 결과: <대상 기능/모듈>

테스트 목록 및 결과:
| 테스트 함수 | 목적(Doxygen @brief 요약) | 기법 | 케이스(긍정/부정) | 대응 설계 요소 | 결과 |
|---|---|---|---|---|---|
| testXxx | ... | 동등분할/경계값분석/결정테이블/상태전이/오류추정 | 긍정/부정 | 함수계약/경계값/조건조합/오류경로 | Pass |

품질 지표 실측 (도구: <사용 도구명>):
| 함수 | 라인수 | 순환복잡도 | 중복 여부 | 판정 |
|---|---|---|---|---|
| ... | ... | ... | ... | 충족/미충족 |

주석 비율: <실측값>% (기준 20% 이상)
Branch 커버리지: <실측값>% (기준 100%)
테스트 성공률: <실측값>% (기준 100%, Pass <N>/<전체 N>)
네이밍 점검: <camelCase 위반 여부>

종합 판정: 완료 조건 14개 항목 각각 충족/미충족 여부
```

## 최종 규칙

```
프로덕션 코드 → 반드시 그 코드를 위한 테스트가 먼저 존재하고, 실패하는 것을 확인했어야 한다.
그렇지 않다면 → TDD가 아니다.
```

사용자의 명시적 승인 없이는 예외를 두지 않습니다. 사용자가 CLAUDE.md와 다른 구현 지침을 새로 제공하면 이 스킬의 기준보다 그 지침을 우선하되, CLAUDE.md 자체와 상충하면 사용자에게 확인을 요청하세요.
