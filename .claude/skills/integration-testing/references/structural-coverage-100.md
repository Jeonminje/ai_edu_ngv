# 구조적 커버리지 목표: 함수 커버리지 100% + Call 커버리지 100%

ISO 26262-6은 소프트웨어 아키텍처(통합) 수준의 구조적 커버리지 지표로 **함수 커버리지(Function Coverage)**와 **Call 커버리지(Call Coverage)**를 공개적으로 알려진 지표로 제시하며, ASIL이 높을수록 권고 강도가 강해집니다. 이 프로젝트는 사용자 지침에 따라 **ASIL과 무관하게 두 지표 모두 100% 달성을 필수 목표**로 합니다.

## 지표 정의

| 지표 | 정의 | "100% 달성"의 의미 |
|---|---|---|
| 함수 커버리지 (Function Coverage) | 통합된 소프트웨어에 존재하는 모든 함수/메서드가 통합시험 실행 중 최소 1회 이상 호출되었는가 | 정의된 모든 함수 각각에 대해, 그 함수 본문의 실행 코드가 최소 1회 실행된 시험 케이스가 존재 |
| Call 커버리지 (Call Coverage) | 정적 호출 그래프상에 존재하는 모든 호출 지점(호출자→피호출자 엣지)이 통합시험 실행 중 최소 1회 이상 실제로 실행되었는가 | 소스 코드에 존재하는 모든 함수 호출 지점 각각에 대해, 그 호출이 실제로 발생한 시험 케이스가 존재 (같은 함수를 호출하더라도 호출 지점이 다르면 별도로 카운트) |

**함수 커버리지와 Call 커버리지의 차이**: 함수 커버리지는 "이 함수가 한 번이라도 실행되었는가"만 확인하지만, Call 커버리지는 "이 함수를 호출하는 모든 개별 호출 지점(같은 함수를 여러 곳에서 호출하는 경우 각각)이 실행되었는가"까지 확인합니다. Call 커버리지 100%가 함수 커버리지 100%보다 강한 조건입니다 — Call 커버리지 100%를 달성하면 함수 커버리지 100%는 자동으로 만족됩니다(모든 호출 지점이 실행되었다면 피호출 함수도 최소 1회는 실행된 것이므로), 단 진입점 함수(엔트리 포인트, 어디서도 호출되지 않고 시험 하네스가 직접 호출하는 함수)는 별도로 확인해야 합니다.

## 측정 방법 (오픈소스 도구 — CLAUDE.md/이 프로젝트 원칙과 동일하게 실측 필수)

Python 3.14 프로젝트에서 두 지표를 실측하는 절차는 다음과 같습니다. 육안 판단이나 "충분히 테스트했다"는 주장으로 대체하지 않습니다.

### 1. 정적 호출 그래프 확보 (Call 커버리지의 "분모")

| 도구 | 용도 |
|---|---|
| `pyan3` | Python 소스를 정적 분석해 함수/메서드 간 호출 그래프(어떤 함수가 어떤 함수를 어디서 호출하는지)를 생성 |
| `code2flow` | 정적 호출 그래프를 시각화/그래프 데이터로 추출하는 대안 도구 |

두 도구 중 하나로 대상 모듈의 전체 호출 지점 목록(호출자 함수, 호출 라인, 피호출 함수)을 뽑아 "분모"로 삼습니다.

### 2. 동적 실행 추적 (Call 커버리지의 "분자")

| 도구 | 용도 |
|---|---|
| `coverage.py` | 라인/브랜치 커버리지 측정 — 함수 본문 라인이 실행되었는지로 **함수 커버리지**를 도출 (`coverage report --show-missing`으로 0% 함수 식별) |
| `viztracer` | 실행 중 발생한 실제 함수 호출 이벤트(호출자→피호출자, 호출 지점 포함)를 기록 — **Call 커버리지**의 분자 데이터 |
| 표준 라이브러리 `trace` 모듈 (`python -m trace --trace`) | `viztracer`를 쓸 수 없는 환경의 대안 — 호출 추적 로그 생성 |

### 3. 커버리지 산출 및 갭 식별

1. `coverage.py`로 통합시험 스위트 전체를 실행하고, 실행되지 않은 함수(0% 커버리지 함수)를 식별합니다 → 함수 커버리지 갭.
2. `viztracer`(또는 `trace`)의 실행 로그에서 실제 발생한 호출 엣지 집합을 만들고, 1단계의 정적 호출 그래프 엣지 집합과 비교해 실행되지 않은 호출 지점을 식별합니다 → Call 커버리지 갭.
3. 두 갭 목록을 표로 정리하고, 각 갭을 없애기 위한 추가 시험 케이스(어떤 통합 단계에서 어떤 인터페이스 호출을 유도할 시험인지)를 설계합니다.
4. 추가 시험 케이스를 반영해 재실행하고, 갭이 모두 해소될 때까지 반복합니다.

## 100%를 달성할 수 없는 경우

- 방어적 코드(도달 불가능한 방어 분기 등 `detailed-design` 스킬의 `defensive-programming-and-error-handling.md`에서 의도적으로 남긴 코드)처럼 정당한 사유로 특정 함수/호출을 실행할 수 없다면, 임의로 100%를 우회 보고하지 말고 **제외 사유와 근거를 명시적으로 문서화**하고 사용자(안전 담당/품질 책임자)의 예외 승인을 요청합니다.
- 예외 승인 없이 커버리지 갭을 "허용 범위"로 자체 판단해 완료로 보고하지 마세요.
- 스텁/드라이버로만 도달 가능한 통합 단위(예: 아직 통합되지 않은 상위/하위 컴포넌트)는 해당 통합 단계에서는 갭으로 보고하고, 이후 단계에서 실제 컴포넌트로 대체되면 재측정합니다.
