# SOLID 원칙과 응집도/결합도 판정 기준

이 프로젝트의 모든 아키텍처 설계는 **높은 응집력, 낮은 결합도, SOLID 원칙 준수**를 예외 없이 만족해야 합니다. 이 문서는 설계를 검토/작성할 때 사용하는 구체적 판정 기준입니다.

## 결합도 (Coupling) — 낮을수록 좋음

아래는 널리 알려진 결합도 분류를 낮은(좋은) 순서부터 높은(나쁜) 순서로 정리한 것입니다. 컴포넌트 설계 시 상위 항목을 목표로 하고, 하위 항목이 발견되면 반드시 리팩터링 방향을 제시합니다.

| 순위 | 결합 유형 | 설명 | 이 프로젝트에서의 허용 여부 |
|---|---|---|---|
| 1 (최선) | 데이터 결합 (Data coupling) | 필요한 데이터만 인터페이스 파라미터로 전달 | 권장 |
| 2 | 스탬프 결합 (Stamp coupling) | 필요 이상의 필드를 가진 자료구조 전체를 전달 | 조건부 허용 — 인터페이스에 불필요한 필드 노출 여부 점검 |
| 3 | 제어 결합 (Control coupling) | 동작을 바꾸는 플래그/모드 값을 전달 | 지양 — 발견 시 대안(전략 패턴, 별도 인터페이스) 제시 |
| 4 | 외부 결합 (External coupling) | 공유된 외부 포맷/프로토콜에 의존 | 외부 인터페이스 경계에서만 허용, 내부 전파 금지 |
| 5 | 공통(공유) 결합 (Common coupling) | 전역 변수/공유 상태를 여러 컴포넌트가 함께 사용 | **금지** — 발견 시 Major 이슈로 보고 |
| 6 (최악) | 내용 결합 (Content coupling) | 다른 컴포넌트의 내부 구현/데이터를 직접 참조·수정 | **절대 금지** — 인터페이스 위반이므로 반드시 재설계 |

**필수 규칙**: 컴포넌트 간 통신은 반드시 정의된 인터페이스를 통해서만 이루어져야 합니다. 직접적인 내부 필드 접근, 전역 상태 공유, 컴포넌트 내부 구현에 대한 암묵적 가정은 결합도 위반으로 간주하고 설계에 포함하지 않습니다. 상세 규칙은 `interface-design.md` 참조.

## 응집도 (Cohesion) — 높을수록 좋음

| 순위 | 응집 유형 | 설명 | 판정 |
|---|---|---|---|
| 1 (최선) | 기능적 응집 (Functional cohesion) | 하나의 잘 정의된 기능만 수행 | 목표 |
| 2 | 순차적 응집 (Sequential cohesion) | 한 요소의 출력이 다음 요소의 입력이 되는 처리 흐름 | 허용 |
| 3 | 통신적 응집 (Communicational cohesion) | 같은 데이터를 다루지만 목적이 다른 기능들이 묶임 | 조건부 허용 |
| 4 | 절차적 응집 (Procedural cohesion) | 실행 순서만으로 묶인 기능들 | 지양 |
| 5 | 시간적 응집 (Temporal cohesion) | 같은 시점(초기화 등)에 실행된다는 이유로만 묶임 | 지양 |
| 6 | 논리적 응집 (Logical cohesion) | 유사 카테고리라는 이유로 묶이지만 실제 동작은 무관 | 지양 |
| 7 (최악) | 우연적 응집 (Coincidental cohesion) | 아무 관련 없는 기능이 임의로 묶임 | **금지** |

**판정 절차**: 컴포넌트를 정의할 때마다 "이 컴포넌트가 존재하는 단 하나의 이유(책임)를 한 문장으로 말할 수 있는가?"를 점검합니다. 두 개 이상의 이유가 필요하면 컴포넌트를 분리해야 합니다 (SRP와 동일한 검사).

## SOLID 원칙 — 컴포넌트/인터페이스 설계 시 검사 항목

| 원칙 | 정의 | 아키텍처 설계 시 검사 질문 |
|---|---|---|
| **S**RP (단일 책임) | 컴포넌트를 변경할 이유는 하나여야 한다 | 이 컴포넌트를 수정해야 하는 시나리오를 나열했을 때 서로 다른 이해관계자/이유가 여러 개인가? |
| **O**CP (개방-폐쇄) | 확장에는 열려 있고, 변경에는 닫혀 있어야 한다 | 새 기능/변형 추가 시 기존 컴포넌트 내부를 수정해야 하는가, 아니면 인터페이스 구현체 추가로 확장 가능한가? |
| **L**SP (리스코프 치환) | 인터페이스의 구현체는 서로 치환 가능해야 한다 | 동일 인터페이스의 다른 구현체로 교체했을 때 호출자의 사전/사후조건 가정이 깨지는가? |
| **I**SP (인터페이스 분리) | 클라이언트가 사용하지 않는 메서드에 의존하지 않아야 한다 | 하나의 인터페이스에 서로 다른 클라이언트가 필요로 하는 메서드가 섞여 있는가? 역할별로 분리 가능한가? |
| **D**IP (의존성 역전) | 상위 모듈은 하위 모듈의 구체 구현이 아니라 추상화(인터페이스)에 의존해야 한다 | 상위 계층/정책 컴포넌트가 하위 계층/세부 구현 컴포넌트를 구체 타입으로 직접 참조하는가, 아니면 인터페이스를 통해 참조하는가? |

## 설계 산출물에 기록하는 방법

템플릿 2장 "아키텍처 설계 원칙"에 위 기준을 어떻게 적용했는지 요약하고, 4장 "컴포넌트 책임"의 각 컴포넌트마다 다음을 함께 기록합니다:

- 응집도 유형(목표: 기능적 응집) 및 판정 근거 한 줄
- 이 컴포넌트가 의존하는 인터페이스 목록(구체 컴포넌트가 아닌 인터페이스만 명시 — DIP 준수 확인)
- SOLID 위반이 의심되는 지점은 갭으로 표시하고 대안을 제시

순환 의존성(Circular dependency)은 결합도·응집도 원칙과 무관하게 **항상 금지**합니다 — 5장 "정적 의존성"에서 의존성 그래프의 비순환성(DAG)을 반드시 확인합니다.
