# 아키텍처 설계 스킬

이 스킬은 A-SPICE 4.1 SWE.2(소프트웨어 아키텍처 설계)와 ISO 26262-6(소프트웨어 개발)에서 공개적으로 알려진 원칙, SOLID 원칙, 결합도/응집도 이론을 결합해 이 프로젝트(자동차 SW, A-SPICE 준수 대상)에 맞는 아키텍처 설계 프레임워크로 재구성해 제공합니다.

**중요**: 아래 내용은 원문 표준의 축약이 아니라 공개적으로 알려진 원칙을 재구성한 실무 참조 자료입니다. 계약/인증 목적의 공식 평가에는 원본 표준 문서를 대조해야 함을 사용자에게 필요 시 안내하세요.

## 이 프로젝트에 적용되는 핵심 제약 (항상 지킬 것, 예외 없음)

1. **높은 응집력 / 낮은 결합도**: 모든 컴포넌트는 기능적 응집을 목표로 하고, 공통/내용 결합은 절대 허용하지 않습니다 → `references/solid-and-coupling-cohesion.md`
2. **SOLID 원칙 준수**: 컴포넌트/인터페이스 설계마다 SRP/OCP/LSP/ISP/DIP를 점검합니다 → `references/solid-and-coupling-cohesion.md`
3. **인터페이스 전용 통신**: 모든 컴포넌트는 인터페이스를 반드시 정의하고, 컴포넌트 간 통신은 정의된 인터페이스로만 이루어져야 합니다. 직접 내부 접근/전역 상태 공유는 금지합니다 → `references/interface-design.md`
4. **변경 유연성**: 가변점을 식별하고 격리해, 요구사항 변경이 특정 컴포넌트에 국한되도록 설계합니다 → `references/architecture-principles.md`
5. **A-SPICE/ISO 26262 준수**: SWE.2 BP와 ISO 26262-6 아키텍처 설계 원칙(모듈화, 캡슐화, 오류 격리, ASIL 독립성)을 만족해야 합니다 → `references/architecture-principles.md`
6. **아키텍처 구조는 반드시 후보 제안 → 사용자 선정 순서로 진행**: 단일안을 임의로 확정하지 않습니다 → `references/architecture-style-candidates.md`
7. **컴포넌트 통합 순서를 반드시 정의**: 정적 의존성 기반으로 순서를 산출하고 전략(상향식/하향식/샌드위치/위험 기반)을 명시합니다 → `references/integration-strategy.md`
8. **회사 지정 설계서 양식(TPL-SWE2-001) 준수**: 산출물은 반드시 아래 양식 구조를 따릅니다 → `references/document-template-mapping.md`

## 사용 절차

1. **작업 유형 파악**: (a) 신규 아키텍처 설계, (b) 기존 아키텍처 리뷰(결합도/응집도/SOLID/인터페이스 점검), (c) 통합 순서만 별도로 정의하는 요청 중 어디에 해당하는지 구분합니다.
2. **입력 확인**: 대상 SW 요구사항 문서, ASIL 배분표, 제약사항을 Read/Grep으로 실제 확인합니다. 없으면 사용자에게 요청하고, 없는 채로 임의로 지어내지 않습니다.
3. **(신규 설계 시) 아키텍처 구조 후보 제안**: `architecture-style-candidates.md` 절차에 따라 2~3개 후보를 비교표로 제시하고, 사용자가 하나를 선택할 때까지 상세 설계로 진행하지 않습니다.
4. **원칙 적용**: `architecture-principles.md`와 `solid-and-coupling-cohesion.md`의 기준을 컴포넌트/인터페이스 설계 전체에 적용합니다.
5. **인터페이스 정의**: `interface-design.md`의 필수 항목에 따라 모든 컴포넌트 쌍의 상호작용을 인터페이스로 명세합니다. 인터페이스 없는 상호작용이 남아있으면 완료로 보고하지 않습니다.
6. **통합 순서 정의**: `integration-strategy.md`에 따라 정적 의존성 기반 통합 순서와 전략을 산출합니다.
7. **양식에 맞춰 산출물 작성**: `document-template-mapping.md`의 섹션 매핑에 따라 Markdown 초안을 작성하고, 실제 `.docx` 반영 절차를 사용자에게 안내합니다.
8. **자체 점검**: 결과 제출 전 아래 "완료 조건"을 모두 확인합니다.

## 완료 조건 (설계서를 완성본으로 보고하기 전 자체 점검)

- [ ] 아키텍처 구조 후보를 2개 이상 제시했고, 사용자가 명시적으로 하나를 선택했는가?
- [ ] 모든 컴포넌트가 단일 책임(기능적 응집)을 가지는가? 공통/내용 결합이 없는가?
- [ ] SRP/OCP/LSP/ISP/DIP를 각 컴포넌트/인터페이스에 대해 점검했는가?
- [ ] 컴포넌트 간 모든 상호작용이 정의된 인터페이스로만 표현되는가 (직접 접근/전역 공유 없음)?
- [ ] 정적 의존성 그래프에 순환이 없는가?
- [ ] 변경 유연성(가변점 격리) 분석이 포함되어 있는가?
- [ ] 컴포넌트 통합 순서와 전략이 명시되어 있는가?
- [ ] 안전 관련 요소가 있다면 ASIL 독립성과 오류 격리가 명시되어 있는가 (없으면 TBD로 표시했는가)?
- [ ] 산출물이 `TPL-SWE2-001`의 섹션 구조를 그대로 따르는가?
