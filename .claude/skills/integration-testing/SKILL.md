# 소프트웨어 통합시험 스킬

이 스킬은 A-SPICE 4.1 SWE.5(소프트웨어 통합 및 통합시험)와 ISO 26262-6(소프트웨어 개발)에서 공개적으로 알려진 통합시험 방법/기법, 구조적 커버리지 지표(함수/Call 커버리지)를 결합해 이 프로젝트에 맞는 통합시험 프레임워크로 재구성한 것입니다.

**중요**: 아래 내용은 원문 표준의 축약이 아니라 공개적으로 알려진 원칙을 재구성한 실무 참조 자료입니다. 계약/인증 목적의 공식 평가에는 원본 표준 문서를 대조해야 함을 사용자에게 필요 시 안내하세요.

## 이 프로젝트에 적용되는 핵심 제약 (항상 지킬 것, 예외 없음)

1. **테스트 베이시스는 아키텍처 설계서**: 인터페이스 명세(6장)와 통합 순서(11장)만을 근거로 시험을 설계·진행합니다. 임의의 인터페이스나 순서를 만들지 않습니다 → `references/test-basis-and-order.md`
2. **ISO 26262-6 기반 시험 방법/기법**: 요구사항기반/인터페이스/결함주입 등 시험 방법과 동등분할/경계값/결정테이블/상태전이/오류추정 케이스 도출 기법을 근거를 밝혀 적용합니다 → `references/iso26262-integration-test-methods.md`
3. **함수 커버리지 100% + Call 커버리지 100% (필수)**: 오픈소스 도구로 실측하고, 갭은 추가 시험 케이스로 해소하거나 명시적 예외 승인을 받습니다 → `references/structural-coverage-100.md`
4. **테스트 성공률 100% (필수, CLAUDE.md)**: 통합시험 케이스 전체가 Pass해야 합니다. 실패한 케이스가 있으면 결함으로 처리하고 해결 전까지 완료로 보고하지 않습니다.
5. **회사 지정 산출물 양식(TPL-SWE5-001/002/003) 준수**: 산출물은 반드시 아래 양식 구조를 따릅니다 → `references/document-template-mapping.md`

## 사용 절차

1. **입력 확인**: 대상 아키텍처 설계서(인터페이스 명세, 통합 전략/순서)를 Read/Grep으로 확인합니다. 없으면 `architecture-designer` 서브에이전트로 먼저 작성하도록 안내합니다.
2. **통합 단계별 시험 설계**: `test-basis-and-order.md`에 따라 통합 순서대로 단계를 나누고, 각 단계에서 새로 결합되는 인터페이스를 확인합니다.
3. **시험 방법/기법 선정**: `iso26262-integration-test-methods.md`에 따라 각 인터페이스에 요구사항기반 시험 + 인터페이스 시험을 기본 적용하고, 오류 계약이 있으면 결함 주입 시험을 추가합니다. 케이스는 동등분할/경계값/결정테이블/상태전이/오류추정 중 근거 기법을 밝혀 도출합니다.
4. **시험 케이스 작성**: `TPL-SWE5-002` 컬럼(Test ID/Trace/Integration Item/Stimulus/Expected Result/Technique/Automation)에 맞춰 작성합니다.
5. **시험 실행 및 커버리지 실측**: Bash로 테스트를 실행하고, `structural-coverage-100.md`의 오픈소스 도구로 함수 커버리지와 Call 커버리지를 실측합니다.
6. **갭 해소**: 커버되지 않은 함수/호출 지점을 식별해 추가 케이스를 설계하고, 100%에 도달하거나 정당한 사유로 예외 승인을 받을 때까지 반복합니다.
7. **결과 기록**: `TPL-SWE5-003` 컬럼(Test ID/Trace/Result/Actual Result/Evidence Locator/Defect ID/Disposition, Run Summary)에 맞춰 결과와 커버리지 실측치를 기록합니다.
8. **자체 점검**: 결과 제출 전 아래 "완료 조건"을 모두 확인합니다.

## 완료 조건 (통합시험 결과를 완성본으로 보고하기 전 자체 점검)

- [ ] 모든 시험 케이스가 아키텍처 설계서의 실제 인터페이스 ID로 추적되는가 (임의 인터페이스 없음)?
- [ ] 시험이 아키텍처 설계서/`TPL-SWE5-001`에 정의된 통합 순서를 그대로 따랐는가?
- [ ] 아키텍처 설계서의 모든 인터페이스가 최소 1개 이상의 시험 케이스로 커버되는가?
- [ ] 각 시험 케이스에 사용 기법과 근거가 명시되어 있는가?
- [ ] 오류 계약이 있는 인터페이스에 결함 주입 시험이 포함되어 있는가?
- [ ] 함수 커버리지 100%를 오픈소스 도구로 실측했는가 (미달 시 갭과 해소 계획 또는 승인된 예외가 있는가)?
- [ ] Call 커버리지 100%를 오픈소스 도구로 실측했는가 (미달 시 갭과 해소 계획 또는 승인된 예외가 있는가)?
- [ ] 전체 통합시험 케이스의 성공률이 100%인가 (Fail 케이스가 없는가)?
- [ ] 산출물이 `TPL-SWE5-001/002/003`의 구조를 그대로 따르는가?

## 다른 테스트 스킬과의 경계

이 스킬은 **A-SPICE SWE.5(소프트웨어 통합 및 통합시험)**만 다룹니다 — 테스트 베이시스는 항상 아키텍처 설계서의 인터페이스와 통합 순서입니다. 아래 인접 영역은 이 스킬의 범위가 아닙니다.

| 대상 | 담당 스킬/에이전트 | 이 스킬과의 차이 |
|---|---|---|
| 함수/모듈 내부 로직 검증 (SWE.4) | `tdd` 스킬 / `coding` 에이전트 | 테스트 베이시스가 상세설계서의 함수 계약이며, 컴포넌트 경계를 넘지 않음 |
| SW 요구사항 기반 자격시험 (SWE.6) | `sw-system-test` 스킬 / `sw-system-tester` 에이전트 | 테스트 베이시스가 아키텍처 인터페이스가 아니라 **SW 요구사항 명세서**이며, 내부 컴포넌트 구조와 무관한 블랙박스 관점 |
| 산출물 관리 체계(CL2) 자체의 감사 | `aspice-auditor` 스킬 / `aspice-cl2-auditor` 에이전트 | 통합시험을 직접 설계/실행하지 않고, 이미 작성된 산출물이 CL2 기준을 만족하는지만 점검 |
