# 요구사항 분석 스킬

이 스킬은 ISO/IEC/IEEE 29148(요구사항 공학), ISO 26262(자동차 기능안전), ISO/IEC 25010(SW 품질 특성)에서 공개적으로 널리 알려진 원칙과 EARS/UML/SysML 같은 업계 표준 표기법을 결합해, 이 프로젝트(자동차 SW, A-SPICE 준수 대상)에 맞는 요구사항 분석·작성 프레임워크로 재구성해 제공합니다.

**중요**: 아래 내용은 원문 표준의 축약이 아니라 공개적으로 알려진 원칙을 재구성한 실무 참조 자료입니다. 계약/인증 목적의 공식 평가에는 원본 표준 문서를 대조해야 함을 사용자에게 필요 시 안내하세요.

## 이 프로젝트에 적용되는 핵심 제약 (항상 지킬 것)

이 프로젝트의 모든 요구사항 작성/리뷰 작업에는 아래 네 가지가 예외 없이 적용됩니다:

1. **ISO 26262 준수**: 안전 관련 기능의 요구사항은 ASIL 등급과 안전 목표 추적성을 갖춰야 합니다 → `references/iso26262-safety-requirements.md`
2. **A-SPICE 준수**: 요구사항 산출물은 A-SPICE CL2 산출물 관리 기준(식별, 버전, 리뷰, 승인)을 만족해야 합니다 → `aspice-auditor` 스킬(SYS.1/SYS.2/SWE.1)과 함께 점검
3. **비기능 요구사항은 ISO 25010 특성으로 분류 + 실행 가능한 검증 방안 동반**: 검증할 수 없거나 현실적으로 수행 불가능한 검증안은 제시하지 않습니다 → `references/nfr-iso25010.md`
4. **모든 이해관계자가 이해할 수 있는 문장**: 개발자뿐 아니라 기획자·QA·고객도 같은 의미로 읽을 수 있어야 합니다 → `references/nfr-iso25010.md`의 "이해 가능성 확인" 및 `references/requirement-quality.md`
5. **양방향 추적성 필수**: 모든 요구사항은 상위(출처)와 하위(설계/테스트)로 끊김 없이 추적 가능해야 합니다 — 추적 링크가 없는 요구사항은 미완성으로 취급합니다 → `references/analysis-process.md`의 "추적성 확립", 시각화는 `references/uml-sysml-notation.md`의 Requirement Diagram

| `references/ears-syntax.md` | EARS 5가지 요구사항 작성 패턴과 예시 | 새 요구사항을 작성하거나 애매한 요구사항을 재작성할 때 |
| `references/analysis-process.md` | 이해관계자 요구사항 → 시스템/SW 요구사항 전개 절차, **양방향 추적성** 확립, 우선순위/충돌 분석 | 요구사항 분석 전체 프로세스를 수행할 때 |

| `references/nfr-iso25010.md` | ISO 25010 특성별 비기능 요구사항 작성 템플릿 + **실행 가능한** 검증 방안 예시, 이해 가능성 확인 기준 | 비기능(품질) 요구사항을 작성/점검할 때 — **항상 적용** |
| `references/uml-sysml-notation.md` | 요구사항 유형별 UML/SysML 다이어그램 선택 기준, Mermaid/PlantUML 예시 | 복잡한 행위/상태/구조/추적 관계를 다이어그램으로 보완할 때 |

## 사용 절차

1. **작업 유형 파악**: (a) 기존 요구사항 리뷰/점검, (b) 새 요구사항 작성/재작성, (c) 이해관계자 요구사항을 시스템/SW 요구사항으로 분석·전개하는 전체 프로세스 중 어디에 해당하는지 구분합니다.
2. **관련 참조 파일 로드**: 리뷰는 `requirement-quality.md`, 작성은 `ears-syntax.md` + `nfr-iso25010.md`(비기능인 경우), 전체 프로세스는 `analysis-process.md`를 중심으로 읽습니다. 안전 관련 기능이면 `iso26262-safety-requirements.md`를 항상 함께 읽습니다.
3. **실제 문서 확인**: 대상 요구사항 문서를 Read/Grep으로 확인합니다. 요구사항이 없는 상태에서 있는 척하지 마세요.
4. **기능 요구사항의 다이어그램화 검토**: 여러 상태/단계/구성요소가 얽힌 기능 요구사항이면 `uml-sysml-notation.md`를 참고해 적합한 다이어그램을 함께 제시할지 판단합니다. 단순한 요구사항까지 무리하게 다이어그램화하지 마세요.
5. **점검/작성 수행**: 아래 "보고 형식"을 따라 결과를 정리하되, 위 "핵심 제약" 5가지를 모두 충족했는지 마지막에 자체 점검합니다.
6. **A-SPICE/품질표준과 연계**: 산출물 관리 자체(식별/버전/리뷰 이력)의 CL2 충족 여부는 `aspice-auditor` 스킬을 사용하세요. 이 스킬은 "요구사항 문장/구조/추적성 자체의 품질"에 집중합니다.

## 보고 형식 (작성 시)

새 요구사항을 작성할 때는 항상:
1. EARS 패턴 중 하나를 명시적으로 선택해 작성하고, 어떤 패턴을 왜 선택했는지 한 줄로 덧붙입니다.
2. 비기능 요구사항이면 ISO 25010 특성 분류와 실행 가능한 검증 방안을 함께 제시합니다.
3. 안전 관련 기능이면 ASIL과 안전 목표 추적 링크를 함께 제시합니다(정보가 없으면 사용자에게 확인을 요청하고 TBD로 표시).
4. 상위 요구사항(출처)과, 가능하다면 예상되는 하위 산출물(설계 요소/테스트 케이스)로의 추적 관계를 명시합니다.
5. 필요 시 `uml-sysml-notation.md`의 다이어그램을 함께 제시합니다.
6. 작성 후 "이 문장을 비전문가가 읽어도 같은 그림을 떠올릴 수 있는가"를 스스로 점검한 결과를 한 줄로 덧붙입니다.

사용자가 특정 회사/프로젝트 템플릿을 제공하면 이 스킬의 형식보다 그 템플릿을 우선하세요.
