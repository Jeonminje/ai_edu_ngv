# 아키텍처 구조 후보 제안 방법

A-SPICE SWE.2 BP "대안 평가"와 이 프로젝트의 요구사항("네가 적절한 아키텍처 구조를 먼저 제안하고, 사용자가 선정")에 따라, 상세 설계서를 작성하기 전에 **반드시** 최소 2~3개의 아키텍처 구조 후보를 사용자에게 제시하고 선택을 받아야 합니다. 후보 없이 임의로 하나의 구조를 확정해 설계서를 작성하지 않습니다.

## 후보 선정 시 고려할 대표 아키텍처 스타일

아래는 널리 알려진 아키텍처 스타일이며, 시스템 특성에 맞는 2~3개를 선별해 제안합니다 (전부 나열할 필요는 없음).

| 스타일 | 핵심 아이디어 | 강점 | 주의점 | 적합한 상황 |
|---|---|---|---|---|
| 계층형 (Layered) | 상위 계층이 하위 계층에만 의존 | 이해하기 쉬움, 책임 분리 명확 | 계층을 관통하는 변경에 취약할 수 있음 | 명확한 추상화 수준 구분이 가능한 시스템 |
| 포트-어댑터 / 헥사고날 (Ports & Adapters) | 핵심 로직을 인터페이스(포트)로 감싸고 외부 기술은 어댑터로 격리 | 외부 기술(HW, DB, 통신) 교체에 강함, DIP 자연스럽게 실현 | 초기 설계 복잡도 증가 | 외부 인터페이스/플랫폼 변경 가능성이 높은 시스템 |
| 컴포넌트 기반 (Component-Based) | 명시적 인터페이스를 가진 재사용 가능한 컴포넌트 조합 | A-SPICE 인터페이스 요구와 정합성 높음 | 컴포넌트 경계 설계 품질에 결과가 좌우됨 | 이 프로젝트의 기본 접근에 가장 가까움 |
| 이벤트 기반 (Event-Driven) | 컴포넌트가 이벤트 발행/구독으로 느슨하게 결합 | 결합도를 크게 낮출 수 있음, 확장 용이 | 동적 동작 추적/디버깅이 어려워질 수 있음, 안전 분석 복잡도 증가 | 비동기 이벤트가 많고 확장성이 중요한 시스템 |
| 파이프-필터 (Pipe & Filter) | 데이터가 처리 단계를 순차 통과 | 데이터 처리 흐름이 명확 | 상태 유지가 필요한 로직에는 부적합 | 신호/데이터 처리 파이프라인 |
| 마이크로커널/플러그인 (Microkernel) | 핵심 기능 + 플러그인으로 확장 기능 분리 | 변경 유연성(OCP) 극대화 | 핵심-플러그인 경계 설계가 어려움 | 기능 변형/옵션이 많은 제품 라인 |
| 계층형 + 안전 파티셔닝 (ASIL 분리) | 서로 다른 ASIL 요소를 별도 파티션/프로세스로 분리 | ISO 26262 독립성 논증 용이 | 파티션 간 통신 오버헤드 | 안전 관련 기능과 QM 기능이 혼재하는 시스템 |

## 제안 절차

1. 대상 시스템의 특성(요구사항, 변경 가능성이 높은 영역, 안전 관련 여부, 실시간성, 배포 환경)을 먼저 파악합니다.
2. 위 표에서 해당 시스템에 적합한 후보 2~3개를 선정합니다. 필요하면 두 스타일을 결합한 혼합안(예: 계층형 + 포트-어댑터)도 하나의 후보로 제시할 수 있습니다.
3. 각 후보에 대해 다음을 표로 정리해 제시합니다:
   - 후보명 / 핵심 구조 요약(간단한 다이어그램 또는 구성요소 나열)
   - 이 시스템의 요구사항 관점에서의 장점
   - 이 시스템의 요구사항 관점에서의 단점/리스크
   - 결합도/응집도, SOLID, 변경 유연성, ASIL 독립성 관점의 평가
4. `AskUserQuestion` 도구 등으로 사용자에게 후보 중 하나를 선택하도록 요청합니다. 사용자가 후보를 수정/조합해달라고 요청하면 반영 후 다시 확인받습니다.
5. 사용자가 최종 선택한 구조를 템플릿 3장 "논리 아키텍처"의 근거로 삼아 상세 설계를 진행합니다. 선택되지 않은 후보와 선정 근거는 15장 "참고자료" 또는 설계 결정 기록에 남깁니다 (A-SPICE "대안 평가" 증거로 필요).

**금지 사항**: 사용자 확인 없이 하나의 아키텍처 구조를 확정하고 전체 설계서를 작성하지 않습니다. 대안 비교 없이 단일안만 제시하는 것은 A-SPICE SWE.2 BP 위반입니다.
