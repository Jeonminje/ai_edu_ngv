# 테스트 베이시스: 아키텍처 설계서의 인터페이스와 통합 순서

이 프로젝트의 통합시험은 **반드시** 승인된 아키텍처 설계서(`architecture-design` 스킬 산출물, `TPL-SWE2-001`)를 유일한 테스트 베이시스로 삼습니다. 임의의 순서나 상상한 인터페이스로 시험을 설계하지 않습니다.

## 인터페이스 기반 테스트 설계

- 아키텍처 설계서 6장 "인터페이스 명세"(6.1 내부 인터페이스, 6.2 외부 인터페이스)에 정의된 각 인터페이스(ID, 제공자, 사용자, 데이터 계약, 사전/사후조건, 시간 제약, 오류 계약)를 그대로 시험 케이스의 근거로 사용합니다.
- 아키텍처 설계서에 없는 인터페이스에 대한 시험 케이스를 만들지 않습니다 — 통합 중 새로 필요한 인터페이스가 발견되면 임의로 시험만 추가하지 말고, 아키텍처 설계서 갱신이 필요함을 사용자에게 알립니다.
- 인터페이스 명세가 불완전(TBD)한 항목은 시험 케이스를 확정하지 말고 갭으로 보고합니다.

## 통합 순서 기반 시험 진행

- 아키텍처 설계서 11장 "통합 전략"(또는 `TPL-SWE5-001` 3장 "통합 항목과 순서")에서 정의한 통합 순서를 **그대로** 따라 시험을 진행합니다. 순서를 임의로 바꾸거나 건너뛰지 않습니다.
- 각 통합 단계마다:
  1. 이번 단계에서 새로 결합되는 통합 항목(컴포넌트 집합)을 확인합니다.
  2. 이번 단계에서 필요한 스텁/드라이버가 아키텍처 설계서의 정의와 일치하는지 확인합니다.
  3. 이번 단계에서 검증 대상인 인터페이스만 시험 범위로 삼습니다(이후 단계에서 결합될 컴포넌트의 인터페이스는 아직 시험하지 않음).
  4. 이전 단계에서 이미 통합된 부분에 대한 회귀 범위(아키텍처 설계서/`TPL-SWE5-001`의 회귀 전략)를 함께 실행합니다.
- 통합 순서가 정의되어 있지 않거나 순환 의존이 남아있는 상태라면, 시험을 진행하지 말고 `architecture-designer`/`architecture-design` 스킬로 통합 순서를 먼저 확정하도록 사용자에게 안내합니다.

## 추적성 확인

- 모든 시험 케이스는 최소 하나의 인터페이스 ID로 추적되어야 합니다 (`TPL-SWE5-002`의 `Trace` 컬럼).
- 아키텍처 설계서의 모든 인터페이스가 최소 하나 이상의 시험 케이스로 커버되는지 확인하고, 커버되지 않은 인터페이스는 갭으로 보고합니다 (인터페이스 커버리지 — `structural-coverage-100.md`의 함수/Call 커버리지와는 별개의 지표이며 둘 다 확인이 필요함).
