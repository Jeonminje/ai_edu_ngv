# 함수 계약 및 공통 자료형 설계

상세설계 수준의 "인터페이스 전용 통신" 실현은 함수 계약(Design by Contract)으로 구체화됩니다. 아키텍처 수준 인터페이스 명세(`architecture-design` 스킬의 `interface-design.md`)를 함수/메서드 시그니처까지 세분화합니다.

## 함수 계약 필수 항목 (템플릿 5장 "핵심 함수 계약")

각 핵심 함수는 아래 항목을 빠짐없이 정의합니다. 확인되지 않은 항목은 TBD로 표시하고 임의로 채우지 않습니다.

| 항목 | 설명 |
|---|---|
| 함수 ID / 시그니처 | 소속 유닛, 함수명, 파라미터 타입, 반환 타입 |
| 입력 (Input) | 파라미터별 의미, 단위, 유효 범위 |
| 출력 (Output) | 반환값 의미, 단위, 유효 범위 |
| 사전조건 (Precondition) | 호출 전 호출자가 보장해야 할 상태/값 범위 |
| 사후조건 (Postcondition) | 정상 종료 시 보장되는 상태/값 |
| 불변조건 (Invariant) | 함수 실행 전후로 유지되어야 하는 조건 (해당 시) |
| 부작용 (Side effect) | 상태 변경, I/O, 전역 자원 접근 — **부작용이 있다면 반드시 명시**, 숨겨진 부작용은 금지 |
| 예외/오류 | 실패 조건과 반환값/예외 타입, 호출자의 처리 책임 |
| 시간 제약 | 최대 실행시간, 호출 주기 제약 (해당 시 — 특히 실시간/안전 관련 함수) |

**규칙**: 사전조건은 호출자가 검증할 항목이고, 사후조건은 이 함수가 보장하는 항목입니다. 두 조건이 모호하게 뒤섞이면 LSP(리스코프 치환) 위반 여부를 판단할 수 없으므로 반드시 분리해 기술합니다.

## 공통 자료형 정의 (템플릿 4장)

- 여러 유닛이 공유하는 데이터 구조, 열거형(enum), 물리 단위, 유효 범위, 불변조건을 한 곳에 모아 정의합니다.
- 자료형 자체에 결합도가 생기지 않도록, 특정 컴포넌트의 내부 구현에 종속된 필드를 공통 자료형에 섞지 않습니다 (스탬프 결합 방지 — `architecture-design`의 `solid-and-coupling-cohesion.md` 참조).
- 직렬화가 필요한 자료형(통신/저장 대상)은 직렬화 규칙(바이트 순서, 인코딩, 버전 필드)을 함께 정의합니다.

## LSP 적용 — 다형적 구현체 설계 시

동일 인터페이스/추상 함수에 대한 여러 구현체(예: 전략 패턴, 드라이버 추상화)를 설계할 때는:

- 구현체마다 사전조건을 원래보다 강화하지 않았는지 확인합니다.
- 구현체마다 사후조건을 원래보다 약화하지 않았는지 확인합니다.
- 위반이 발견되면 호출자가 구현체를 구분해서 처리해야 하므로, 이는 다형성이 아니라 숨겨진 분기이며 아키텍처 수준 인터페이스 설계를 재검토해야 함을 보고합니다.
