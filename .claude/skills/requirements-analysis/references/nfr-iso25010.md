# 비기능 요구사항(NFR) 작성 — ISO/IEC 25010 연계

비기능 요구사항(품질 요구사항)은 **막연한 다짐이 아니라, 측정 가능한 기준 + 실제로 수행 가능한 검증 방안**을 갖춰야 완성된 것으로 봅니다. 이 참조 파일은 `sw-quality-standards` 스킬의 ISO 25010 품질 특성(`iso25010.md`, AI 요소가 있으면 `iso25059.md`도 함께)을 이용해 비기능 요구사항을 작성하는 절차와, 검증 방안을 반드시 실행 가능하게 만드는 방법을 다룹니다.

## 작성 절차

1. **품질 특성 식별**: 작성하려는 비기능 요구가 ISO 25010의 어느 특성/부특성에 해당하는지 먼저 분류합니다 (`sw-quality-standards`의 `iso25010.md` 표 참조). 특성을 먼저 정하면 "무엇을 빠뜨렸는지"를 점검하기 쉬워집니다.
2. **측정 가능한 기준 수립**: 부사(빠르게/충분히/안정적으로 등)를 숫자·조건·범위로 치환합니다.
3. **EARS 패턴으로 문장화**: `ears-syntax.md`의 패턴(주로 유비쿼터스 또는 상태 기반)을 사용해 조건과 기준을 명확히 표현합니다.
4. **검증 방안 명시**: 아래 "검증 방안 선택 기준"에 따라 이 요구사항을 어떻게 확인할지 함께 기술합니다. 검증 방안이 없으면 요구사항이 아니라 희망사항입니다.
5. **이해 가능성 확인**: 아래 "이해 가능성 확인" 기준으로 비전문가도 읽고 무엇을 요구하는지 알 수 있는지 검토합니다.

## 품질 특성별 작성 템플릿과 검증 방안 예시

각 행은 예시이며, 실제 수치/기준은 프로젝트 맥락에 맞게 사용자와 함께 확정해야 합니다 — 임의로 숫자를 만들어 넣지 말고, 수치가 없으면 TBD로 표시하고 사용자에게 확인을 요청하세요.

| ISO 25010 특성 | 요구사항 문장 예시 (EARS) | 실행 가능한 검증 방안 |
|---|---|---|
| 성능 효율성 – 시간 반응성 | "시스템은 검색 요청에 대해 200ms 이내(95th percentile)로 응답해야 한다." | 부하 테스트 도구(예: JMeter)로 지정된 동시 사용자 수 조건에서 응답시간을 측정하고 95th percentile 값을 확인 |
| 신뢰성 – 가용성 | "시스템은 월간 가동률 99.9% 이상을 유지해야 한다." | 운영 모니터링 로그 기반으로 월간 다운타임을 집계해 가동률 계산 (실측 필요 — 설계 단계에서는 목표 수치로 검토) |
| 사용성 – 학습 용이성 | "신규 사용자는 별도 교육 없이 10분 이내에 핵심 기능(주문 생성)을 완료할 수 있어야 한다." | 사용성 테스트: 신규 사용자 표본(예: 5~8명)을 대상으로 작업 완료 시간을 측정하고 평균/중앙값이 기준을 만족하는지 확인 |
| 보안성 – 기밀성 | "시스템은 저장된 개인정보를 AES-256 이상으로 암호화해야 한다." | 코드/설정 리뷰 및 정적분석 도구로 암호화 알고리즘·키 길이 확인, 저장소 덤프 검사 |
| 유지보수성 – 시험 용이성 | "핵심 모듈의 단위 테스트 분기 커버리지는 80% 이상이어야 한다." | 커버리지 측정 도구(예: JaCoCo, gcov)로 CI 파이프라인에서 자동 측정 |
| 이식성 – 설치 용이성 | "시스템은 사전 정의된 설치 스크립트 실행만으로 15분 이내에 설치가 완료되어야 한다." | 정해진 환경(OS/버전)에서 설치 절차를 실제로 수행하고 소요 시간 측정 |
| 안전성 – 고장 안전 | "WHILE 자율주행 모드일 때, IF 주 제어기가 응답하지 않으면, THEN 시스템은 1초 이내에 안전 정지 모드로 전환해야 한다." | HIL(Hardware-in-the-Loop) 환경에서 주 제어기 응답 차단을 주입(fault injection)하고 전환 시간 측정 |

## 검증 방안 선택 기준 — "실행 불가능한 검증안 금지"

검증 방안을 제안하기 전에 아래를 스스로 확인하고, 하나라도 걸리면 검증 방안을 다시 설계하세요:

- [ ] **측정 수단이 실제로 존재하는가**: 언급한 도구/장비/환경이 실제로 프로젝트에서 확보 가능한가 (존재하지 않는 가상의 도구를 전제로 하지 않는다)
- [ ] **재현 가능한가**: 동일한 절차를 반복해 같은 방식으로 확인할 수 있는가 (일회성 주관적 판단에 의존하지 않는다)
- [ ] **판정 기준이 이분법적으로 명확한가**: 결과를 보고 통과/불통과를 다툼 없이 판정할 수 있는가
- [ ] **비용/시간이 프로젝트 규모에 비례하는가**: 예를 들어 소규모 내부 도구에 대해 수백 명 규모의 사용성 연구를 요구하는 등 과도한 검증을 제안하지 않는다
- [ ] **검증 시점이 명확한가**: 설계 리뷰 단계에서 확인 가능한 것과, 실제 구현/배포 후에만 측정 가능한 것을 구분해 표시한다 (예: 가동률은 설계 단계에서 "목표 수치 타당성 검토"로, 운영 후 "실측"으로 이원화)

검증 방안이 이 중 하나라도 만족하지 못하면, 요구사항 자체를 더 구체적으로 좁히거나(측정 가능한 대리 지표로 치환) 검증 시점/방법을 조정해 제안하세요. "추후 협의" 같은 표현으로 검증 방안을 얼버무리지 마세요.

## 이해 가능성 확인 — "모든 사람이 이해할 수 있어야 한다"

요구사항은 개발자뿐 아니라 기획자, 품질보증 담당자, 고객 등 다양한 배경의 이해관계자가 읽고 같은 의미로 이해할 수 있어야 합니다.

- **평이한 문장 구조**: 한 문장에 하나의 요구만 담고(단일성), 이중 부정·중첩 조건절을 피합니다.
- **전문 용어 최소화 및 정의**: 불가피하게 전문 용어/약어를 쓸 경우 문서 내 용어집이나 각주로 정의합니다 (예: "95th percentile"이 무엇을 뜻하는지 비전문가를 위해 한 줄 설명 추가).
- **수치의 맥락 제공**: "200ms"처럼 숫자만 제시하지 않고 "사용자가 지연을 체감하지 않는 수준" 같은 맥락을 함께 적어 비전문가도 왜 그 수치인지 이해하게 합니다.
- **자체 검증**: 요구사항을 작성한 뒤 "이 문장을 다른 배경의 사람에게 보여줬을 때 같은 그림을 떠올릴 수 있는가"를 스스로 반문하세요. 특정 역할(예: 개발자)만 이해할 수 있는 구현 지향적 표현이 섞여 있다면 요구사항이 아니라 설계로 분류해 별도 문서로 옮기세요.

## 점검 시 체크리스트 (요약)

- [ ] ISO 25010 특성/부특성으로 분류되어 있는가
- [ ] 정량적 기준이 있는가 (부사 표현 없음)
- [ ] EARS 패턴으로 단일하게 표현되어 있는가
- [ ] 실행 가능한 검증 방안이 함께 명시되어 있는가 (위 5개 기준 통과)
- [ ] 비전문가도 읽고 이해할 수 있는 문장인가
