# 요구사항 분석 프로세스

이해관계자 요구사항에서 시작해 시스템/SW 요구사항으로 전개되는 흐름과, 그 과정에서 수행해야 할 분석 활동을 정리합니다. A-SPICE SYS.1(이해관계자 요구사항 도출)/SYS.2(시스템 요구사항 분석)/SWE.1(SW 요구사항 분석)과 대응되며, 이 참조 파일은 "그 프로세스 안에서 요구사항을 어떻게 분석·전개할 것인가"에 초점을 둡니다. 프로세스 산출물 자체의 존재/관리 여부 감사는 `aspice-auditor` 스킬을 사용하세요.

## 전개 흐름

```
이해관계자 요구사항 (Stakeholder Requirements)
        │  분석·구조화·정제
        ▼
시스템 요구사항 (System Requirements)
        │  기능 배분 (아키텍처 요소별)
        ▼
소프트웨어/하드웨어 요구사항 (SW/HW Requirements)
```

각 화살표 단계마다 아래 분석 활동을 수행합니다.

## 1. 구조화 (Structuring)

- 요구사항을 기능적(Functional) / 비기능적(Non-functional, 품질 요구사항) / 제약(Constraint)으로 분류합니다.
- 비기능 요구사항 분류 시 `sw-quality-standards` 스킬의 ISO 25010 품질 특성 목록을 참조하면 누락된 카테고리(예: 이식성, 보안성)를 쉽게 찾을 수 있습니다.
- 상위-하위 계층 구조(예: 에픽 → 기능 요구 → 세부 요구)를 명확히 합니다.

## 2. 상호 영향 분석 (Interaction/Impact Analysis)

- 요구사항 간 의존관계(A가 충족되어야 B가 의미 있음)를 식별합니다.
- 상충하는 요구사항(같은 자원/동작에 대해 다른 조건을 요구)을 식별하고, 우선순위 또는 조건 분기로 해소합니다.
- 하나의 요구사항 변경이 다른 요구사항에 미치는 영향을 기록합니다 (변경관리 시 SUPP.10과 연계).

## 3. 검증 기준 정의 (Verification Criteria)

- 각 요구사항에 대해 "이것이 충족되었는지 어떻게 확인할 것인가"를 정의합니다 — 테스트, 분석, 검사, 시연(demonstration) 중 적합한 방법을 선택합니다.
- 검증 기준이 정의되지 않은 요구사항은 `requirement-quality.md`의 "검증 가능함" 위반이며, 이후 SWE.4~6/SYS.4~5 테스트 설계 단계에서 반드시 문제가 됩니다.

## 4. 우선순위화 (Prioritization)

- MoSCoW(Must/Should/Could/Won't) 또는 유사 기법으로 우선순위를 부여합니다.
- 우선순위는 이해관계자 합의를 거쳐야 하며, 임의로 개발팀이 정하지 않습니다.

## 5. 추적성 확립 (Traceability)

- **상위 추적 (Backward Traceability)**: 각 요구사항이 어떤 이해관계자 요구/상위 요구에서 왔는지.
- **하위 추적 (Forward Traceability)**: 각 요구사항이 어떤 설계 요소·테스트 케이스로 이어지는지.
- 양방향 추적성이 끊긴 요구사항(고아 요구사항, orphan requirement)이나, 요구사항 없이 존재하는 설계/테스트(근거 없는 산출물)를 모두 찾아 보고하세요.

## 6. 검증/합의 (Validation)

- 작성된 요구사항(또는 그 집합)을 이해관계자와 함께 검토해 실제 니즈를 정확히 반영하는지 확인합니다.
- 리뷰 결과와 합의 이력을 남깁니다 (SUPP.4 공동검토와 연계).

## 분석 결과 보고 시 체크리스트

- [ ] 모든 이해관계자 요구사항이 최소 1개 이상의 하위 요구사항으로 전개되었는가 (커버리지 갭 없음)
- [ ] 기능/비기능/제약이 명확히 구분되어 있는가
- [ ] 상충하는 요구사항이 식별되고 해소되었는가
- [ ] 모든 요구사항에 검증 기준이 있는가
- [ ] 우선순위가 이해관계자 합의를 거쳤는가
- [ ] 양방향 추적성이 끊김 없이 유지되는가
