# SW 시스템 테스트 케이스 생성

## 개요

SW 요구사항 명세서 기반으로 SW 시스템 테스트 케이스를 생성하기 위한 방법론 스킬입니다. A-SPICE 4.1 **SWE.6(소프트웨어 자격시험, Software Qualification Test)**에 해당합니다 — 통합된 소프트웨어 전체가 SW 요구사항을 만족하는지 블랙박스 관점으로 검증합니다. 이 스킬은 "무엇을 근거로, 어떤 기법으로, 어떤 원칙으로" 테스트 케이스를 설계할지에 대한 방법론만 정의합니다. 요구사항 분석, 사용자와의 확인, 실제 산출물(xlsx) 작성은 이 스킬을 사용하는 에이전트(예: `sw-system-tester` 서브에이전트)가 수행합니다.

## 기반지식

- **ISO 26262 Part 6**: 소프트웨어 단위/통합/시스템 테스트에 대한 요건. 특히 ASIL 등급이 할당된 요구사항은 판정기준의 전 분기(경계값, 조건 조합)를 빠짐없이 검증해야 합니다.
- **A-SPICE SWE.4, SWE.5, SWE.6**: 소프트웨어 단위 검증, 통합 시험, 시스템 시험에 대한 Base Practice. 양방향 추적성(요구사항 ↔ 테스트 케이스)과 표준화된 시험 절차를 요구합니다.
- **ISO 29119 및 ISTQB**: 테스트 시나리오·테스트 케이스 설계 프로세스와 용어 체계(긍정/부정 분류 등)의 근거로 사용합니다.
- **ISO 25000 (SQuaRE)**: 비기능(품질) 요구사항을 분류하는 기준입니다. 비기능 테스트 케이스는 이 표준의 품질 특성(예: 기능적합성, 성능효율성, 호환성, 사용성, 신뢰성, 보안성, 유지보수성, 이식성)별로 그룹화합니다.

## 적용 대상 테스트 기법

기법의 정의는 **`sw-quality-standards` 스킬의 `references/iso29119.md`(ISO/IEC/IEEE 29119 Part 4)를 단일 출처**로 사용합니다 — `tdd`, `integration-testing` 스킬과 동일한 명칭·정의를 그대로 씁니다. 이 스킬에서 기법을 다시 정의하지 않고, 요구사항 성격에 따라 어떤 기법을 선택할지만 정리합니다. 각 테스트 케이스의 "사용 기법" 항목에 실제로 적용한 기법을 명시합니다.

| 요구사항 성격 | 선택할 기법 |
|---|---|
| 검증기준에 수치·범위·임계값이 있음 | 경계값 분석 — 경계값 미만/경계값/경계값 초과를 각각 별도 케이스로 도출 |
| 입력 도메인을 유효/무효로 나눌 수 있음 | 동등분할 — 클래스별 대표값 도출 |
| 여러 조건의 조합에 따라 결과가 달라지고, 조건 수가 적어 전수 조합이 가능함 | 조합 테스트 (전 조건 조합) — PICT `/o:max` 옵션 사용 |
| 조건·값의 조합 수가 많아 전수 조합이 비현실적임 | 페어와이즈 테스팅 — PICT로 조합 생성 |
| 정상 범위의 극단, 동시성/타이밍 등 일반 기법으로 포착 안 됨 | 엣지 케이스 테스팅 |
| 상태를 가진 기능(로그인 세션, 모드 전환 등) | 상태 전이 테스팅 |
| 유사 시스템의 결함 이력이나 QA 경험에 근거 | 오류 추정 / 탐색적 테스팅 (경험 기반 기법) |

## 다른 테스트 스킬과의 경계

이 스킬은 **A-SPICE SWE.6(소프트웨어 자격시험)**만 다룹니다 — 테스트 베이시스는 항상 SW 요구사항 명세서이며, 소프트웨어 내부 구조(아키텍처 컴포넌트, 상세설계, 소스 코드)를 알지 못해도 설계 가능한 블랙박스 테스트만 다룹니다. 아래 인접 영역은 이 스킬의 범위가 아닙니다.

| 대상 | 담당 스킬/에이전트 | 이 스킬과의 차이 |
|---|---|---|
| 함수/모듈 내부 로직 검증 (SWE.4) | `tdd` 스킬 / `coding` 에이전트 | 화이트박스 관점, 테스트 베이시스가 상세설계서의 함수 계약 |
| 컴포넌트 간 인터페이스, 통합 순서 검증 (SWE.5) | `integration-testing` 스킬 / `integration-tester` 에이전트 | 테스트 베이시스가 SW 요구사항이 아니라 아키텍처 설계서의 인터페이스 명세이며, 함수/Call 커버리지 100%라는 구조적 커버리지 목표를 가짐 |
| 산출물 관리 체계(CL2) 자체의 감사 | `aspice-auditor` 스킬 / `aspice-cl2-auditor` 에이전트 | 테스트를 직접 설계/실행하지 않고, 이미 작성된 산출물이 CL2 기준을 만족하는지만 점검 |

## 작성 원칙

- 의미 없이 테스트 커버리지 수치 달성만을 목적으로 하는 케이스는 생성하지 않습니다.
- 테스트의 예상 결과를 임의로 가정하지 않습니다. 명세서에 근거가 없다면 이 스킬을 사용하는 에이전트가 사용자에게 확인을 받아야 합니다.
- 프로젝트에서 정한 테스트 커버리지 목표(예: CLAUDE.md에 명시된 기준)를 준수합니다.
- 실행자가 그대로 재현할 수 있는, 실행 가능한 테스트 케이스만 작성합니다.
- 기법 선택이나 커버리지 범위 설정이 판단하기 어려운 경우 임의로 결정하지 말고, 이 스킬을 사용하는 에이전트를 통해 사용자 검토를 받습니다.
- 명세서에 직접적 근거는 없으나 QA 관점에서 추가를 제안하고 싶은 테스트 케이스는 테스트 케이스명 끝에 "(제안)"이라고 표시해 구분합니다.
- 사용한 테스트 설계 기법을 각 케이스에 명시합니다.
- CLAUDE.md에 따라 이 프로젝트는 **테스트 성공률 100%**를 요구합니다. 케이스를 실행해 Fail이 나오면 성공률을 맞추기 위해 케이스를 임의로 삭제/완화하지 말고, 결함으로 기록하고 해결될 때까지 완료로 보고하지 않습니다.

## 도구 사용

- 페어와이즈 조합을 생성할 때는 오픈소스인 PICT를 사용합니다.
- 전수 조합(모든 조건의 조합)을 생성할 때는 PICT의 `/o:max` 옵션을 사용합니다.

## 산출물 구조

- 기능 요구사항에 대한 테스트 케이스: "테스트 케이스" 시트
- 비기능 요구사항에 대한 테스트 케이스: 별도의 "비기능 테스트 케이스" 시트, ISO 25000 품질 특성별로 구분
- 요구사항 원문에 없거나 원문보다 엄격하게 사용자 확인을 거쳐 확정한 판정기준: "확정 근거" 열에 확정 일자와 승인 주체 기록
