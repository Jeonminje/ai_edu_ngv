# 정직한 테스트 작성 (obra/superpowers "Writing Good Tests" 기반)

**언제 읽는가**: 테스트를 새로 작성하거나 수정할 때, Mock을 추가할 때, 테스트용 정리(cleanup)/헬퍼 메서드를 추가할 때.

이 참조는 [obra/superpowers](https://github.com/obra/superpowers)의 `writing-good-tests.md`를 이 프로젝트(Python/`unittest`)에 맞게 재구성한 것입니다.

## 개요

테스트는 특정한 깨짐(break)을 잡기 위해 존재합니다. 아래 두 원칙이 전부를 지배합니다.

```
1. 모든 테스트는 자신이 잡는 깨짐을 이름으로 설명할 수 있어야 한다.
2. 모든 테스트는 실제 대상(진짜 코드)을 실행해야 한다.
```

엄격한 TDD(테스트를 먼저 작성하고 실제 코드에 대해 실패를 확인)는 이 두 원칙을 자연스럽게 만족시킵니다 — 실패를 이미 증명했기 때문입니다. Mock은 실제 의존성이 느리거나 외부 자원일 때만 사용합니다.

## 원칙 1: 깨짐을 이름으로 설명하기

테스트 본문을 쓰기 전에 먼저 답하세요: **이 테스트를 실패하게 만드는 프로덕션 코드 변경은 무엇이며, 그것은 버그인가 설계 결정인가?** 잘못된 분기, 누락된 부작용, 잘못된 인자, 경계 조건, 깨진 계약을 잡을 때 테스트는 존재 이유를 갖습니다.

**기대값은 독립적으로 도출합니다.** 리터럴 값과 손으로 계산/확인한 픽스처를 사용하세요 — `want` 값이 리터럴인 표 기반(table-driven) 테스트가 선호되는 형태입니다. 테스트 대상 코드(또는 그 헬퍼)로 계산한 기대값은 그 코드가 무엇을 하든 항상 통과합니다.

```python
# 잘못된 예: 거울 단언 — 같은 빌더로 양쪽을 계산 → 항상 참
expected = buildSearchQuery({"tag": "urgent"})
self.assertEqual(buildSearchQuery({"tag": "urgent"}), expected)

# 올바른 예: 손으로 도출한 리터럴
self.assertEqual(buildSearchQuery({"tag": "urgent"}), 'tag:"urgent"')
```

**변경 감지기(change detector)를 만들지 마세요.** 의도적인 설계 결정만 이 테스트를 깨뜨릴 수 있다면(상수값, 정확한 메시지 문구, 내부 구조 등) — 재설계 시에는 울리고 실제 버그에는 잠들어 있는 테스트입니다. 결정 그 자체가 아니라 그 결정에 의존하는 동작을 테스트하세요: `self.assertEqual(MAX_RETRIES, 5)`가 아니라 "실패한 호출이 5번 재시도되고 6번째 시도는 일어나지 않는다"를 검증합니다.

**동작을 테스트하고, 텍스트를 테스트하지 마세요.** 스크립트/스킬/설정 파일이 특정 문자열을 포함하는지 확인하는 것은 소스가 소스라는 것만 증명합니다. 스크립트는 통제된 입력으로 실행해 출력/부작용/종료 코드를 검증하세요.

**당신의 코드를 테스트하고, 프레임워크를 테스트하지 마세요.** 경계에서 당신의 코드가 맺는 계약(등록한 라우트, 발행한 쿼리, 생성한 페이로드)을 테스트합니다. 상위(upstream) 동작은 그 유지보수자의 테스트 몫입니다(대표적 예: "내 라우터가 등록된 핸들러를 호출하는지" 검증 — 이것은 프레임워크의 테스트지 당신의 테스트가 아닙니다). 상위 동작이 예상과 달라 실제로 놀랐다면, 그 가정을 명시하는 좁은 범위의 특성화(characterization) 테스트 하나만 작성하세요. 같은 경계 원칙은 코드 내부에도 적용됩니다: 생성자, getter, 상수, 단순 위임(forwarding)은 검증/정규화/기본값 설정/유도/강제/부작용 중 하나를 수행할 때만 테스트 대상이 됩니다 — 그렇지 않다면 그것에 의존하는 첫 소비자 쪽 결과를 단언하세요.

### 게이트 함수 (테스트 작성 전 자체 점검)

```
테스트 본문을 쓰기 전에:
  이 테스트를 실패하게 만드는 프로덕션 코드 변경을 이름으로 말할 수 있는가.

  말할 수 없다면            → 관찰 가능한 동작 중심으로 재설계
  "소스 텍스트가 바뀌었다"   → 산출물을 직접 실행하고 그 효과를 단언
  의도적 결정만 잡아낸다     → 변경 감지기다; 그 결정에 의존하는 동작을 테스트

  기대값이 테스트 대상 코드 없이 도출되었는지 확인한다.
  테스트 대상 코드/헬퍼의 로직을 재사용한다면:
    리터럴 값이나 손으로 확인한 픽스처로 교체한다.
```

## 원칙 2: 실제 대상을 실행하기

**Mock 자체에 대한 단언은 무의미합니다.** Mock이 존재하면 통과하고 없으면 실패하는 단언은 그 컴포넌트에 대해 아무것도 증명하지 않습니다. 실제 컴포넌트의 동작을 단언하세요 — Mock을 검증하고 있다면 Mock을 걷어내거나 그 단언을 삭제하세요.

```python
# 올바른 예: 실제 동작 검증
self.assertTrue(response.context["is_authenticated"])

# 잘못된 예: Mock 존재 여부만 확인
self.assertTrue(mockAuthService.called)
```

**적절한 수준에서 Mock 하세요.** 실제 메서드를 대체하기 전에 그 모든 부작용을 먼저 파악하고, 느리거나 외부 자원인 부분만 Mock하며 테스트가 의존하는 부분은 실제로 남겨두세요. 확신이 없으면 실제 구현으로 먼저 실행해 무엇이 실제로 일어나는지 관찰하세요.

```python
# 잘못된 예: Mock이 중복 감지 로직이 읽는 설정 파일 쓰기까지 삼켜버림
with patch("toolCatalog.discoverAndCacheTools", return_value=None):
    ...

# 올바른 예: 느린 서버 기동만 Mock, 설정 파일 쓰기는 실제로 남김
with patch("mcpServerManager.MCPServerManager"):
    ...
```

**더블(double)을 구체적으로 만드세요.** 인자, 호출 횟수, 순서가 계약의 일부라면 그것을 단언하세요 — 아무거나 받아주는 페이크는 아무것도 검증하지 못합니다. 각 분기(성공/오류/잘못된 형식)마다 별도의 픽스처나 스파이를 두어 잘못된 분기가 기대값을 만족시키지 못하게 하세요.

**Mock 데이터는 실제 구조를 완전히 반영하세요.** 테스트가 실제로 읽는 필드만이 아니라 문서화된 전체 필드를 Mock하세요. 부분적인 Mock은 다운스트림 코드가 누락된 필드를 읽을 때 조용히 실패합니다 — 테스트는 통과하지만 통합은 깨집니다.

**프로덕션 클래스에는 프로덕션 메서드만 둡니다.** 테스트에서만 필요한 정리(cleanup) 코드를 프로덕션 클래스의 `destroy()` 같은 메서드로 넣지 마세요. 자문하세요: 이 메서드는 테스트에서만 호출되는가? 이 클래스가 이 자원의 생명주기를 소유하는가? 답이 "아니오"라면 테스트 유틸리티로 옮깁니다.

**복잡한 Mock보다 실제 컴포넌트를 선호하세요.** Mock 설정이 테스트 로직보다 커지거나, Mock이 실제 컴포넌트의 메서드를 놓치거나, Mock이 바뀔 때마다 테스트가 깨진다면 실제 컴포넌트를 사용하는 통합 테스트로 전환하세요.

### 게이트 함수 (Mock/헬퍼 추가 전 자체 점검)

```
Mock이나 테스트 헬퍼를 추가하기 전에:
  실제 메서드의 부작용을 나열하고, 테스트가 의존하는 것은 실제로 남긴다.
  느리거나 외부인 수준만 Mock한다.

  Mock 응답이 실제 구조를 완전히 반영하는가.

  테스트에서만 호출되는 메서드는 프로덕션 클래스가 아니라 테스트 유틸리티에 둔다.

  Mock 자체를 단언하려는가?
    Mock을 걷어내거나 그 단언을 삭제한다.
```

## 구현과 함께 배포되는 테스트

TDD 사이클(실패하는 테스트 → 최소 구현 → 리팩터링)이 곧 "완료"의 정의입니다. 그 동작에 필요한 테스트만 배포하세요 — 사소한 코드와 사람이 읽는 문서는 테스트를 받을 필요가 없고, 절차를 만족시키기 위해 쓴 테스트는 영원한 유지보수 비용이 됩니다.

## 뮤테이션 체크 (완료 전 필수)

작업을 마치기 전, 프로덕션 코드를 머릿속으로 변형(mutate)해 보세요. 현실적인 변형마다 최소 하나의 테스트가 실패해야 합니다.

- 잘못된 상수/인자
- 잘못된 분기 핸들러
- 누락된 상태 변경/부작용
- 빈 값 또는 기본값 반환
- 0, 빈 값, None, 권한 없음, 잘못된 형식 입력에 대한 검증 누락

어떤 변형도 잡아내지 못하는 테스트는 그 동작이 보호받지 못하고 있다는 뜻이거나, 테스트 자체가 동어반복(tautological)이라는 뜻입니다.

## 빠른 참조

| 상황 | 행동 |
|---|---|
| 테스트를 작성할 때 | 그것이 잡는 깨짐(버그, 결정이 아님)을 이름으로 말하기 |
| 기대값을 만들 때 | 손으로 도출. 테스트 대상 코드로 계산하지 않기 |
| 스크립트/문서를 테스트할 때 | 실행/소비자 관점에서 검증. 텍스트를 grep하지 않기 |
| 의존성에 대한 테스트를 쓰려 할 때 | 그들의 문서화된 메커니즘이 아니라 내 경계 계약을 테스트 |
| Mock된 요소를 단언하려 할 때 | 실제 컴포넌트를 테스트하거나 Mock을 걷어내기 |
| 메서드를 Mock하려 할 때 | 부작용을 먼저 파악하고, 느리거나 외부인 수준만 Mock |
| Mock 응답을 만들 때 | 실제 구조를 완전히 반영 |
| 테스트에서만 쓰는 정리 코드가 필요할 때 | 테스트 유틸리티에 두기 |
| Mock 설정이 비대해질 때 | 실제 컴포넌트를 쓰는 통합 테스트로 전환 |
| 테스트 파일을 마칠 때 | 뮤테이션 체크 실행 |

## 경고 신호

- 준비(setup)와 단언이 같은 객체를 공유해 항상 같음을 보장
- 패닉/크래시/셀렉터 누락으로만 실패할 수 있는 테스트
- 의도적인 모든 변경에서 실패하지만 실수로 인한 깨짐에는 절대 실패하지 않는 테스트
- 기대값이 루프/빌더/헬퍼 뒤에 숨겨져 있음
- 소스 텍스트를 grep하거나, 제거된 심볼이 계속 없는지만 확인
- 프레임워크만 남아 있어도 여전히 의미 있는 테스트
- 커버리지를 위해서만 존재하고 부작용이나 결과를 확인하지 않는 테스트
- `*-mock` 테스트 ID를 확인하거나 Mock을 제거하면 실패하는 단언
- 테스트 파일에서만 호출되는 메서드
- Mock 설정이 테스트의 절반 이상을 차지하거나 왜 필요한지 설명할 수 없음
- "혹시 몰라서" Mock을 추가함
