# ISO 26262 관점의 요구사항 분석 (기능 안전)

ISO 26262(도로차량 기능안전 표준)를 준수해야 하는 프로젝트에서는 일반 요구사항 품질 기준(`requirement-quality.md`) 위에 안전 관련 추가 규율이 적용됩니다. 이 참조 파일은 "요구사항 분석/작성" 관점에서 ISO 26262가 요구하는 것을 정리합니다. 프로세스 산출물 자체의 존재 여부는 `aspice-auditor` 스킬과 함께 점검하세요 (ISO 26262와 A-SPICE는 별개 표준이지만 자동차 SW 프로젝트에서는 흔히 함께 적용됩니다).

## 안전 요구사항 계층 구조

```
아이템 정의 (Item Definition)
        │
위험원 분석 및 위험성 평가 (HARA) → 안전 목표 (Safety Goal) + ASIL 등급
        │
기능 안전 요구사항 (Functional Safety Requirement, FSR)  [Part 3]
        │
기술 안전 요구사항 (Technical Safety Requirement, TSR)   [Part 4]
        │
        ├── 하드웨어 안전 요구사항 (HW Safety Requirement) [Part 5]
        └── 소프트웨어 안전 요구사항 (SW Safety Requirement) [Part 6]
```

각 계층의 요구사항은 상위 계층으로부터 **ASIL을 상속**하며, 양방향 추적성이 끊김 없이 유지되어야 합니다. 요구사항 분석 시 이 계층 중 어디에 해당하는지 먼저 식별하세요.

## ASIL (Automotive Safety Integrity Level)

- QM(품질관리, 안전 무관) → ASIL A → ASIL B → ASIL C → ASIL D(가장 엄격) 순으로 엄격도가 높아집니다.
- 요구사항에는 반드시 ASIL 등급이 명시되어야 합니다 (또는 QM으로 명시적으로 분류).
- **ASIL 분해(Decomposition)**: 하나의 안전 목표를 여러 독립적인 요구사항으로 분해해 각각 더 낮은 ASIL로 구현할 수 있습니다(예: ASIL D → ASIL B + ASIL B, 독립성 입증 필요). 분해가 사용되었다면 독립성(freedom from interference) 근거가 함께 문서화되어야 합니다.

## 안전 요구사항 작성 시 추가로 확인할 것

일반 품질 특성(`requirement-quality.md`)에 더해 안전 요구사항은 다음을 만족해야 합니다:

| 항목 | 확인할 것 |
|---|---|
| **ASIL 표기** | 요구사항에 ASIL 등급이 명시되어 있는가 |
| **안전 목표 추적성** | 해당 요구사항이 어느 안전 목표(Safety Goal)에서 유래했는지 상위 추적 링크가 있는가 |
| **고장 대응 정의** | "고장 시 무엇을 해야 하는가"(safe state로의 전환, 경고, 기능 제한 등)가 명시적으로 정의되어 있는가 |
| **고장 허용 시간 (Fault Tolerant Time Interval)** | 위험 상태로 전이되기까지 허용되는 시간이 정의되어 있는가 (해당 시) |
| **독립성/분리 요구사항** | ASIL이 다른 기능들이 서로 간섭하지 않도록 하는 요구(메모리 분리, 시간 분리 등)가 필요한지 검토되었는가 |
| **검증 방법의 엄격도** | ASIL 등급이 높을수록 요구되는 검증 방법(리뷰 독립성, 테스트 커버리지 기준 등)이 강화되는가 — 예: ASIL C/D는 MC/DC 커버리지(`sw-quality-standards`의 ISO 29119 화이트박스 기법 참조)가 요구되는 경우가 많음 |

## 요구사항 유형과 ISO 26262의 관계

- **기능 요구사항**이 곧 안전 요구사항이 되는 경우가 많습니다 — 예: "시스템은 충돌 위험 감지 시 자동 제동해야 한다"는 기능 요구이자 안전 목표를 충족하는 FSR일 수 있습니다. 요구사항을 분석할 때 이 요구가 HARA에서 도출된 안전 목표와 연결되는지 확인하세요.
- 안전과 무관한(QM) 요구사항이라도 안전 요구사항과 상호작용(같은 자원 공유, 같은 인터페이스 사용)한다면 그 상호작용이 안전 목표를 훼손하지 않는지 분석해야 합니다.

## 점검 시 활용 방법

1. 요구사항 명세서에서 안전 관련 기능(제동, 조향, 전원 관리 등)을 다루는 요구사항을 먼저 식별합니다.
2. 각 요구사항에 ASIL 등급과 안전 목표 추적 링크가 있는지 확인합니다. 없으면 Major 갭으로 지적하세요 — 이는 감사에서 가장 자주 지적되는 항목입니다.
3. 고장 대응 동작이 EARS의 "원치 않는 동작(Unwanted Behaviour, IF-THEN)" 패턴으로 명확히 표현되어 있는지 확인합니다.
4. ASIL 분해가 사용된 경우 독립성 근거 문서가 함께 있는지 확인합니다.
